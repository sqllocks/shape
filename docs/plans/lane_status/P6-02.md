## Early publication for P5-01 (pushed in `faa18bf`)

`shape.chaos.inject_anomalies(batch, *, fraction, seed, kinds=None, protect=())`, documented in
`docs/CHAOS.md` ("Stable entry point"): keeps the schema and the row count; returns the changed
rows, kinds and columns and a plugin `ChaosReport`; deterministic per `(batch, fraction, seed)`;
`protect` keeps a stream's key and event-time columns intact. P5-01 derives one seed per batch.
The baseline's `stream` command never calls its chaos package for `--anomaly-fraction` (its
own point-anomaly generator handles it), so this entry point is Shape's design over the value
category's schema-preserving kinds, not a port. P5-01 only needs this one function.

## Acceptance, item by item

1. **Port of `chaos/` (engine, config, categories) as `shape.chaos` built-ins, exactly six
   categories.** Done: schema, value, file, referential, temporal, volume (5, 6, 8, 2, 4 and 3
   sub-mutations). No category was added or left out. The scheduler (`should_inject`, three
   escalations, four intensity presets, overrides, warmup) is ported with the same draw order.
2. **Per-mutator parity on mutation rates and types, harness under
   `benchmarks/vs_spindle/chaos_1to1/`.** Done; `verify.py` runs, with the same input, config and
   seeds in both tools: every sub-mutation alone at the four intensity presets (112 jobs of 100
   seeds), each category's `mutate` as a whole at the four presets (28 jobs of 300 seeds; schema
   also at a day before the breaking-change day), and the engine's injection schedule (13 jobs:
   three escalations x four presets, an override, a disabled engine; 40 seeds x 100 days x six
   categories each). One classifier (`chaos_common.py`) reads the mutation off each tool's
   (input, output) pair, so nothing comes from either tool's own bookkeeping.
   - **Types: exact** (set of kinds equal, inside the category's taxonomy, a sub-mutation alone
     yields only its own kind, and cells hit by two mutations of one call are classified
     `overlap`, which the harness compares like a kind and which is not a fault).
   - **Rates: derived tolerance, not tuned.** Frequencies: two-proportion z-test; mean affected
     row rate: Welch with a floor of one row; `z = Phi^-1(1 - 0.001 / (2 m))` over the m = 792
     comparisons (Bonferroni, family-wise 0.1%), so z = 4.846. The derivation is in the
     docstring of `verify.py`. Nothing was adjusted after seeing a result.
   - **Result (full run, `docs/plans/evidence/P6-02/chaos_1to1_full.json`): PASS.** 153 jobs,
     20,083 runs per tool, 792 comparisons, 0 problems. Every comparison has a difference of exactly
     0, and every run's output is identical cell for cell in both tools (20,083 / 20,083). That
     identity is reported by the harness and is not a criterion: it holds because both tools'
     numpy releases give the same random stream (the baseline venv is numpy 2.4.6), so the pass
     side of the tolerance was never exercised by this run.
   - **The harness can fail** (`--negative-control`, log in `docs/plans/evidence/P6-02/`): with
     Shape's row shares raised by 20% the same comparison fails on 32 comparisons (the value and
     temporal sub-mutations) and the control exits 0 only because it did.
3. **Entry point for P5-01, documented in docs/ and pushed early.** Done (above).

## Differences from the baseline, all forced or documented

- **Arrow's one type per column:** `wrong_types` and `retype_column` render the column as text
  (the baseline keeps mixed Python objects); `out_of_range` and `negative_amounts` give a float64
  column and keep nulls as nulls in integer columns (the baseline's pandas upcasts to float NaN);
  `orphan_fks` keeps an integer column's type when the orphan ids fit. These are in `docs/CHAOS.md`.
  The classifier compares a number with its text, so these representation differences do not
  count as a different mutation.
- **The baseline's `apply_all` drops its referential result** (it assigns the mutated tables to a
  local and returns only the frame), so asking for referential chaos there had no visible
  effect. Shape's `apply_all` returns a `ChaosResult` with `.table`, `.tables` (the referential
  result) and `.events`. The random draws are unchanged.
- **Config defaults are copied per instance** (the baseline shares one nested dict between
  configs). Not observable in parity runs.
- Timestamp columns with a time zone are not "datetime" columns (as in the baseline's
  `select_dtypes(include="datetime")`); a timestamp column named in `date_columns` is used.

## Findings for the lead (nothing was changed)

- **`shape.plugins.kit.check_chaos` requires the mutated batch to keep the schema.** By design
  the schema, value (`wrong_types`) and volume (empty batch, spike) categories, and the file
  category (bytes in, bytes out), do not. The wrappers satisfy the `ChaosMutator` Protocol
  (`name`, `mutate(batch, seed) -> (batch, ChaosReport)`) and the tests assert determinism, an
  honest report and an unmodified input for all six, but only `temporal` passes `check_chaos`
  as written. The Protocol is a P2 contract; I did not change it or the kit. A decision is needed
  if the kit should check the other five differently.
- The baseline pins pandas 3.0.6; its `select_dtypes(include="object")` also selects the new
  `str` dtype (with a deprecation warning), so string columns are chaos targets as intended.
