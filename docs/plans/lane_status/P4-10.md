  `--seed`, `--format summary|csv|tsv|jsonl|parquet|excel|sql|delta`, `-o DIR`, `--dry-run`, `--json`,

  `from-ddl` writes), so `from-ddl` is integrated: `shape from-ddl x.sql -o x.gen.json && shape generate
  x.gen.json -f csv -o out/`. Unknown domain, scale, mode or a missing `-o` exit 2.
  **Old use of `generate`:** `shape generate --rows N` (no target) still prints N demo rows (kept, its test is
  unchanged). **`--from X.shape` is reserved for P4-08**: it parses and exits 2 with "not available yet".
- **`shape describe`**, **`shape list`**, **`shape presets`** (`--json` on each).
- **Retail `star` mode:** the baseline's `retail_star` schema is imported by P4-01a's importer into
  `plugins/shape-domains/.../data/retail/schema_star.json` (`export_retail.py` writes and `--check`s both
  schemas); the plugin has `modes = ("3nf", "star")` and `definition(mode)`; `load_domain(name, mode=)`,
  `domain_modes()`, `DomainModeError`. Plugin API v1 is unchanged for a domain that offers only one schema.
- **`shape.api.generate(domain, scale=, seed=, mode=)`** returns the `GenerationResult` (`.tables`: name to
  `pyarrow.Table`; `result["order"]`). Also takes a `GenSchema` or schema dict. The earlier
  `generate(shape_model, n, seed, relationships)` form works as before.
- **Structured JSON logging and run metrics** (`src/shape/runlog.py`, a port of the baseline's
  `observability.py`: `JsonFormatter`, `configure_logging`, `RunMetrics` with `start_table/end_table/
  record_event/finish/to_json`, plus `begin/current/set`), for **every command**: global options
  `--log-json`, `--log-level`, `--metrics FILE` (before the command) or `SHAPE_LOG_JSON`, `SHAPE_LOG_LEVEL`,
  `SHAPE_METRICS`. Logs `command started` / `command finished` as JSON lines on stderr; the metrics file holds
  the command, exit code, seconds and (for `generate`) domain, mode, scale, seed, format, rows, tables.
  **Module name:** it is `shape.runlog`, not `shape.observability`: the old Prometheus `shape.observability`

- **`shape validate FILE`** (`src/shape/cli/validate.py`): a generation schema (`schema_version`, `model`,

#### Why medium misses, and what was tried (§6.5 round 1 of 2 used)

Spindle's own CLI is much faster than the harness path P4-07 timed (medium 6.8 s here against 9.2 s on the P4-07
machine; large 99 s against 215 s), so the same Shape run that was 13.5x in-process is 6.8x against the CLI.
Shape's 0.99 s: about 0.32 s of imports that both tools pay (numpy 0.06, pyarrow 0.08, pandas 0.17: pyarrow
imports pandas the first time it builds an array, and Shape uses `pa.array` everywhere), about 0.45 s generate
and write (CPU-saturated: 2.0 s CPU in 0.99 s wall), the rest CLI, plugin discovery and exit. To reach 10x the
whole process would have to take 0.68 s.
Done: single entry-point scan (-45 ms), lazy `shape.generation` (-50 ms CPU of imports). Tried and rejected:
keeping pyarrow from importing pandas by a `sys.modules` entry (pyarrow gets `None` back instead of an
ImportError and crashes; reverted, nothing of it remains); importing pandas in a thread (slower).
What is left is not tuning-sized for this work package: either the generation critical path (customer -> address
-> order -> order_line, then the single-threaded `order_line` write; P4-07 territory) or avoiding
`pa.array` in the whole engine so pandas is never imported. **Escalation:** per §6.5/§0.4 the gate is unchanged;
the lead/owner decides between (a) a second optimisation round on the generation path and a pandas-free array
construction path, (b) accepting medium GEN-CLI with the numbers above. Not recorded in §2.3 (lane rule).

### Where the 0.35 s came from (profiled with `-X importtime`, py-spy, a stamped timeline and cProfile first)

1. **pandas is never imported** (about 0.16 s of imports): pyarrow imports it on the first `pa.array`,
   `Array.to_numpy`, `pa.scalar` or `Array.fill_null` (the compute functions build a scalar through the same shim).
   `shape.generation.arrowkit` builds those from buffers (`array`, `to_numpy`, `scalar`, `fill_null`, `raw_numpy`) and
   hands everything it does not handle (objects, mixed lists, timezones, decimals, ...) to pyarrow unchanged. The engine,
   strategies and both kernels' generation functions use it. Tests: 54 cases against pyarrow (including a real bug that
   the test found: `datetime64[D]` needs an int32 buffer), and a subprocess test that `shape generate` and the pure
   array path never import pandas (`tests/cli/test_generation_cli.py`, `tests/generation/test_arrowkit.py`), in both
   kernels. Behaviour with pandas present, and for every other feature, is pyarrow's own.
2. **Start-up work off the critical path** (about 0.07 s): sinks and sources load on first use (PEP 562; the Delta sink
   dragged in the cloud libraries and `ssl`), the Parquet sink loads on a writer thread while the first tables are
   generated, `shape.artifact` is no longer imported by the dispatcher, the plugin host reads a package's name once
   instead of once per entry point (13 ms), the argparse parser is built once, a single-chunk reference column is not
   copied (8 ms).
3. **Critical path of the generation** (about 0.1 s): `order_total` (`sum_children`) is accumulated while the child
   table's chunks are made (`StreamedAggregate`: same row-order additions as the single native pass, so the result is bit
   for bit the same; anything else falls back to the ordinary pass); the leading business rule is repaired on a helper
   thread as soon as its tables exist when no `computed` column and no earlier rule is in the way (`EarlyRules`);
   Parquet row groups are 256k rows (were 1M) so the encoder of a streamed table starts as chunks arrive; `write_engine`
   leaves one core to the writer threads (the encoder of `order_line`, one thread, is what the run waits for; 3
   generation threads + writers measured better than 4 at 4 vCPU, 0.682 s against 0.694 s in interleaved runs;
   `SHAPE_THREADS`, when set, is used as given). Tests compare both passes with the plain order on schemas that do and do
   not allow them (`tests/generation/test_streamed_passes.py`).
4. **Process start and end** (about 0.05 s): a plain `shape generate` run as the program (no `--log-json`/`--metrics`)
   switches the garbage collector off (10 ms) and ends the process once the last file is closed and the output flushed
   (`os._exit` after a flush) instead of freeing about 400 MB of tables and unloading modules (about 40 ms). Tests: the
   files, JSON output and exit codes are complete; an `atexit` handler still runs for every other command and when
   metrics or logs are on.

Tried and not kept (measured, no effect beyond noise): glibc malloc tunables (mmap/trim thresholds, arena count,
hugetlb), mimalloc/jemalloc pool settings, a thread that pre-faults memory, thread niceness for the generation threads,
smaller first row groups, `write_batch_size`/page-size options, a dictionary-size limit, more or fewer chunks per level.
Not changed because the plan fixes them: snappy and dictionary encoding (T-17); statistics stay on.

### What the owner may want to look at

* The early process exit and the disabled collector apply only to a plain `shape generate` run from the command line;
  `main(argv)` calls from Python or tests, other commands, and runs with `--log-json`/`--metrics` are unchanged.
* `SHAPE_THREADS` unset now means "every core less one" while *writing* (`write_engine`); `Engine.generate()` and the
  GEN-IN path keep every core. Large medium-size runs are the same or slightly slower with 3 threads (large 4.4 s with 3,
  4.3 s with 4 in an interleaved check), so the choice favours the gated workload.
* The default Parquet row group is 262,144 rows (file about 0.7% larger); documented in `docs/GENERATION_ENGINE.md`.
* The remaining time (0.646 s): about 0.19 s of imports (python 13 ms, numpy 64 ms, pyarrow 29 ms plus 38 ms for
  `pyarrow.compute`, shape 30 ms), 0.03 s to the first chunk, 0.25 s of generation levels (customer, address, order,
  order_line, strictly in that order), then the single-threaded Parquet encode of `order_line` (about 0.19 s of CPU, which
  starts when its first row group arrives). Options for more, if wanted: (a) strategy-level dependency tracking so
  `order_line` starts before `order` is complete (only its `promotion_id` lookup reads `order`; estimated 50-70 ms, a
  larger change in engine and strategies); (b) a native (Rust) generation core with no numpy/pyarrow imports; neither is
  needed for the gate.
