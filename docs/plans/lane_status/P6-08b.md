## What changed

- `plugins/shape-sqlserver/src/shape_sqlserver/profiler.py`
  1. `null_rate`, `cardinality_ratio`, `is_unique` (and so `is_enum`) divide by the rows actually
     sampled. The profile records it: every table has `sampled_rows`, the dataset has
     `sampling` (`method`, `requested_rows`, a note naming the sample-based fields).
     (The Shape profile is a plain dict, so these are extra keys; the core model is unchanged.
     They round-trip through `shape.save`/`load` and `to_html`/`summary` work: tested.)
  2. With no declared FKs, relationships the sampled data shows are reported (the baseline's
     heuristic result was dead code). Precedence: **declared keys are authoritative and nothing
     is inferred beside them; otherwise data evidence first, then name inference for every column
     the data did not link.** A name never replaces a data link. Data links come first in
     `relationships`.
  3. Every link (declared, data, name) sets the column's `is_foreign_key` and `fk_ref_table` as
     well as `detected_fks` and `relationships` (`_mark_foreign_keys`).
- `catalog.py`: `table_stem` (see "Other copied defects").
- `docs/plugins/sqlserver.md`: sampling and key-inference sections describe the correct behaviour.
- `benchmarks/vs_spindle/db_1to1/intentional.py` (new) + `verify.py`: the parity allow-list.
- Tests: `plugins/shape-sqlserver/tests/test_profiler.py`, `test_emulator.py`.

Note on fix 2: Shape's data-based detector only links a `*_id` column to the table of that name
when the values are contained in the parent's key, so with the data and the names both pointing
at a table they always agree on the parent; the combination matters for columns only one of them
links, and for the `parent_columns` (data: the key detected in the sample; names: the catalog key).

## Other places where the plugin copied a baseline defect

Fixed (clearly wrong, small):

- **`dim`/`fact` stripped anywhere in a table name** (`table.replace("dim", "")`), used by the key
  guess and by name inference (`sandimas` became `sas`). Now only a leading `dim`/`fact` (and one
  following `_`) is removed (`catalog.table_stem`); `dimcustomer`, `factsales` behave as before.
  Test: `test_dim_and_fact_inside_a_table_name_are_not_stripped`. No parity scenario has such a
  table, so the parity run is unaffected; this is not in the parity allow-list because no case
  exercises it. A name that merely starts with `dim` or `fact` (`factory`, `dimension`) is still
  stripped: indistinguishable from `factsales` without a separator.

Described for the lead (not fixed; each changes behaviour beyond a small fix):

1. **The sample is the first N rows** (`SELECT TOP n`, no `ORDER BY`). A table stored in date or
   key order is sampled from its start, so distributions are biased. A random sample
   (`TABLESAMPLE`/`NEWID()`) would be non-deterministic and costlier: a design decision.
2. **An unsampled column reports `null_rate` 0.0 and `cardinality_ratio` 0.0** (`--sample-rows 0`,
   unreadable table, empty table): indistinguishable from "no nulls" except through
   `sampled_rows == 0`. Making them null changes the profile schema.
3. **`is_unique` on a nullable column**: distinct count over sampled rows counts nulls in the
   denominator, so a column unique among its values but with at least 1% nulls is not unique. On
   a very small sample (`--sample-rows 1`) every column is unique. Both follow from the sampled
   definition now documented; a null-aware rule would be a change to the profile's meaning.
4. **`is_enum` is true for any column with at most 50 distinct values**, including a unique text
   column of a 10-row table (enum frequencies of 0.1 each). Same rule as the core profiler.
5. **Declared keys switch inference off for the whole schema.** If any table declares a foreign
   key, undeclared `*_id` columns elsewhere are not linked. Documented as "declared keys are
   authoritative"; mixing would be a policy change.
6. **Name inference is crude**: the `id` suffix matches words such as `paid` or `valid`
   (only if a table `pa`/`val` exists), links are single-column, a `_id`-less `*Id` form is
   matched case-insensitively only against `dim`-prefixed or plain table names, and the data
   detector in the core profiler itself needs `*_id` naming and a detected unique key in the
   sampled parent.
7. **A guessed primary key** (no declared one) can be a foreign-key column (the "any column
   ending in `id` or `key`" fallback picks the first such column).
