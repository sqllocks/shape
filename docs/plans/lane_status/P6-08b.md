## Other places where the plugin copied a baseline defect

Fixed (clearly wrong, small):

- **`dim`/`fact` stripped anywhere in a table name** (`table.replace("dim", "")`), used by the key
  guess and by name inference (`sandimas` became `sas`). Now only a leading `dim`/`fact` (and one
  following `_`) is removed (`catalog.table_stem`); `dimcustomer`, `factsales` behave as before.
  Test: `test_dim_and_fact_inside_a_table_name_are_not_stripped`. No parity scenario has such a
  table, so the parity run is unaffected; this is not in the parity allow-list because no case
  exercises it. A name that merely starts with `dim` or `fact` (`factory`, `dimension`) is still
  stripped: indistinguishable from `factsales` without a separator.

Described for the lead (not fixed; each changes behaviour beyond a small fix):

1. **The sample is the first N rows** (`SELECT TOP n`, no `ORDER BY`). A table stored in date or
   key order is sampled from its start, so distributions are biased. A random sample
   (`TABLESAMPLE`/`NEWID()`) would be non-deterministic and costlier: a design decision.
2. **An unsampled column reports `null_rate` 0.0 and `cardinality_ratio` 0.0** (`--sample-rows 0`,
   unreadable table, empty table): indistinguishable from "no nulls" except through
   `sampled_rows == 0`. Making them null changes the profile schema.
3. **`is_unique` on a nullable column**: distinct count over sampled rows counts nulls in the
   denominator, so a column unique among its values but with at least 1% nulls is not unique. On
   a very small sample (`--sample-rows 1`) every column is unique. Both follow from the sampled
   definition now documented; a null-aware rule would be a change to the profile's meaning.
4. **`is_enum` is true for any column with at most 50 distinct values**, including a unique text
   column of a 10-row table (enum frequencies of 0.1 each). Same rule as the core profiler.
5. **Declared keys switch inference off for the whole schema.** If any table declares a foreign
   key, undeclared `*_id` columns elsewhere are not linked. Documented as "declared keys are
   authoritative"; mixing would be a policy change.
6. **Name inference is crude**: the `id` suffix matches words such as `paid` or `valid`
   (only if a table `pa`/`val` exists), links are single-column, a `_id`-less `*Id` form is
   matched case-insensitively only against `dim`-prefixed or plain table names, and the data
   detector in the core profiler itself needs `*_id` naming and a detected unique key in the
   sampled parent.
7. **A guessed primary key** (no declared one) can be a foreign-key column (the "any column
   ending in `id` or `key`" fallback picks the first such column).

### The decisions, with their cost

- **FIX-4 method:** `SELECT TOP n * ... ORDER BY (CAST(CHECKSUM(key) AS bigint) * 1327217885) % 2147483647,
  key`. Key = declared primary key; with none, every hashable column. A table with at most n rows is
  read whole (no `ORDER BY`), which keeps small tables identical to the baseline. Deterministic, no
  seed. **Plain `CHECKSUM(key)` is not enough and I first wrote it that way:** the real server
  returns an integer unchanged, so the sample was ids 1..1000 again. The stand-in's hash (crc32)
  hid this; the real-server test caught it. The multiplication fixes it. Cost, measured in this
  container (SQL Server 2022, 5M-row table with a PK, 1000 rows): 3.2 s (PK) / 2.9 s (all
  columns) against 4 ms for the first rows; one full scan, n rows of memory. Only
  `CHECKSUM`/`CAST`/`ORDER BY`/`TOP`; **Azure SQL and Fabric SQL were not available to test here.**
  If a server rejects the query the first n rows are read, a warning is logged, and
  `tables[...].sample_method` says `first rows (fallback)`. `TABLESAMPLE` rejected: page-granular, not
  determined by the data alone.
- **Profile additions (extra keys of the profile dict, the core model is otherwise unchanged):**
  `sampling.method`, `tables[...].sample_method`, `relationships[...].evidence`,
  `columns[...].fk_evidence`.
- **FIX-6 threshold:** unique means distinct / non-null above 0.99 (the existing rule, now over the
  non-null values); null below 2 non-null values.
- **FIX-9 beyond the lead's wording:** a column named like the table's *singular* also counts
  (`orders` -> `order_id`); without it the most common naming would report no key. Also kept: the
  identity column first, and `<table>_key`. A column is ruled out only if the sample *shows* a
  null or a repeat; with no sampled rows nothing is ruled out (name evidence only).
- **FIX-8 consequence:** a name in one case with no separator (`customerid`) has no word boundary
  and is not matched any more. Documented.
- `is_enum` (at most 50 distinct values) is **unchanged**, as instructed: it is the core profiler's
  rule (T-22). Note: the merged tracker mentions a "P1-18 enum rule" decision; that is the core's,
  I did not touch it.

## For the lead

- `is_enum` (at most 50 distinct values): unchanged, as instructed (core profiler's rule, T-22).
  It is false when nothing was sampled (the rule over 0 distinct values), not null.
- Behaviour changes users may notice: a table with no declared key and no plausible key column now
  has an empty `primary_key` (the baseline guessed the first `*id`/`*key` column, else the first
  column); `customerid` (one case, no separator) is no longer read as an id; profiling a table
  larger than the sample costs one full scan (about 3 s per 5M rows here).
- `shape.check` treats a `unique` or `max_null_rate` rule on an unknown (null) value as "cannot
  judge", not a violation; `shape.diff` skips an unknown rate. A stricter reading ("unknown fails
  the contract") is a one-line change in `contracts/v1.py` if you prefer it.
- Not fixed, not asked: the baseline's name inference still links a column to a table only when
  the stem equals the table name or `dim` + the name (no `fact`, no plurals), and links are
  single-column.
