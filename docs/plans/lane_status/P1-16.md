# P1-16 — Cheaper likelihood, bitwise-exact (lane/P1-16)

Status: **built; awaiting lead verification.** The likelihood is bitwise-equal to the reference and much cheaper;
equivalence holds on every default dataset. No gate or tolerance was changed. Read the timing section before
counting on G1: fitting is no longer the largest cost on D3 Parquet, but D4 CSV is still short of 10x on this machine.

## What was built (all in `rust/shape-kernel/`)
1. **Chunked, parallel passes over `pairwise_sum`'s block tree** (`fit.rs`, `Plan`/`Eval`). numpy sums a contiguous array
   by a fixed recursion (blocks of at most 128, left half rounded down to a multiple of 8). The leaves of that tree are
   independent, so every pass of the lognormal fit (shape/scale, dL/dloc, nnlf, penalized nnlf) runs chunk by chunk:
   elementwise work, numpy's `log` and the leaf sums on a cache-sized chunk of whole leaves, on the rayon pool for
   columns of 2^18 rows or more; the leaf sums are recombined by the same additions in the same order (an add program
   built from the recursion), so every value equals the whole-array evaluation bit for bit.
   Also: the squared-deviation sum no longer writes an array; `shape_scale` and `dl_dloc` are memoised by `loc` (the root
   finder asks again for its bracket ends); the support check uses the smallest value only; the KS statistic scan is
   chunked (maximum with sticky NaN merges exactly, first maximum kept).
2. **numpy's own `log`/`exp` loops without the GIL** (`numpy_loops.rs`). Inside the profiler's thread pool every chunk
   waited for the GIL (each `numpy.log` call needs it). The CPU-dispatched `d->d` inner loops of `np.log`/`np.exp`
   (SVML on x86-64 Linux) are read once from the public `PyUFuncObject`, cross-checked against numpy's Python-level view
   of the ufunc, and enabled only if a bitwise self-test against numpy passes (numpy 2.x only). The results are numpy's
   by construction; otherwise, or with `SHAPE_NUMPY_LOOPS=python`, numpy is called through Python as before (a pass
   whose `log` input could be non-positive then stays on the calling thread, where numpy's error state is `ignore`).
   `_kernel.numpy_loops_mode()` reports which route is active.
3. **A finding, fixed:** the lognormal log-density used `SQRT2PI` = 2.5066282746310007 (one ulp above), while numpy's
   `np.sqrt(2*np.pi)` (the reference, and scipy) is 2.5066282746310002. The Rust likelihood therefore never equalled the
   numpy reference to the last bit: **44 of 175 probes differed in the last digits of the log-likelihood** before. It now
   uses numpy's value (`NP_SQRT_2PI`); the Kolmogorov code keeps its own constant. No fitted parameter or score changed on
   any of the 82 real float columns or the 140 fuzzed fits.

Not done, on purpose: a Rust port of SVML's `log` (proprietary-table assembly, CPU-specific; calling numpy's own routine
is bitwise-identical by construction); skipping evaluations in the bracket search or Nelder-Mead (the evaluation sequence
is the reference's and each value feeds the next decision; the 600 Nelder-Mead evaluations are all distinct, so there is
nothing to memoise there).

## Differential tests (bitwise, fuzzed)
- Rust (`fit.rs` tests, debug run 54 s): chunked passes vs the previous whole-array evaluation (`shape_scale`, `dl_dloc`,
  `ll`, `nnlf`, `penalized_nnlf`) on six fuzzed families, 14 sizes from 20 to 150k, chunk sizes of 1, 7 and the default
  leaves, locs below, at and above the data minimum; invalid parameters (NaN, zero, negative, underflow); `pw_combine` vs
  `pairwise_sum` for n in 0..1300 and up to 1M; Nelder-Mead fallback and the whole root-finding fit vs the whole-array
  fit (`ref_lognorm_fit`); chunked KS scan vs the serial scan including NaN. Mutation check: replacing the leaf sums by a
  naive sum makes three of them fail.
- Python (`tests/kernel/test_fit_bitwise.py`, 15 tests, 7 s): native vs the numpy reference twin
  (`shape.profile.reference.numerics`), **bit for bit**, on shape/scale/dL/dloc/loglik at six locs for five families and
  seven sizes (up to 300k, above the parallel threshold), and on whole fits (distribution, every parameter, fit score) for
  ten families and six sizes; native loops vs numpy-through-Python in subprocesses.
- Before/after on real data: the pristine kernel (git `c3b7537`, built in a worktree) and this one give identical
  `fit_distribution` output (all parameters and scores, `==` on the dicts) on all 82 float columns of D3 and D4.

## What remains in fitting, for the lead and P1-17
- The remaining per-evaluation cost is numpy's `log` (about 45%, on its SVML loop; unavoidable for bitwise equality),
  `pairwise_sum` (7%), and the elementwise arithmetic including two or three IEEE divisions per element (divisions run at the
  same throughput at any SIMD width on this CPU, so wider vectors do not help). The evaluation sequence of the bracket search
  and of Nelder-Mead is the reference's; D3 `latency_ms` is an ill-conditioned fit (the root is near loc = -8.4e5, 64 evaluations)
  and D4 has eight columns that run Nelder-Mead to its 600-evaluation cap (about 4.4 s of the 6.7 s of fit CPU on D4).
- `fit_score` sorts the full column again (`sorted_copy`, 13 ms per D4 column, about 1.7 s of CPU over the 123 small D4 fits),
  although P1-15's `count_numeric` already produces a sorted copy: passing it into `fit_distribution` would save that, but it
  changes the kernel API, so it is outside this work package.
- A value-deduplicating evaluation (compute per distinct value, gather, then sum over the original order) would stay exact on
  rounded columns such as `latency_ms` (about 480k distinct of 5M) but not on high-cardinality ones; not done.
