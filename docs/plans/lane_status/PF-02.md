## PF-02 — Fabric notebooks, productized: built

### What was built
- `src/shape/integrations/fabric/spark.py` (importable, strict mypy, no pyspark import at module load):
  `profile_distributed(df, *, name, top_n, partitions)`. Each Spark partition streams its Arrow batches
  (`mapInArrow`) into a bounded-mode kernel `ProfileState` and emits its `snapshot()`; the driver reads the
  snapshots one partition at a time (`toLocalIterator`, so nothing piles up against
  `spark.driver.maxResultSize`), restores each with `from_snapshot` and folds it with `merge` (the T-14
  HLL/KLL/SpaceSaving merges), in partition order, then finalizes with the engine's own `table_entry`: the
  result is the same `profile-engine-v1` document the single-process engine returns. Empty table, all-null
  partitions, schema disagreement between partitions and bad arguments are handled and tested.
- `integrations/fabric/notebooks/shape_profile_distributed.ipynb` (new, from `build_notebooks.py`): PySpark
  notebook with the same parameters as the others plus `mode` (`distributed` default, or `exact`: the
  driver-only exact profile of `shape_profile_spark`, the only mode that checks a contract or diffs a
  baseline) and `partitions`. **The distributed mode refuses `contractPath`/`baselinePath`** and reports
  `"checked": false` in its exit value, so it cannot pass a gate it did not evaluate.
- Rust-kernel wheel: the Python notebook's install cell is now `%pip install --find-links builtin
  "sqllocks-shape==0.9.0"`: pip takes the platform wheel when `builtin/` has one that fits, else the pure wheel.
  All profile notebooks print `Shape <v>, kernel: <rust|python>` and return `kernel` in the exit value.
- `pyproject.toml`: `pyspark>=4.0,<5` added to `[dev]` (the plan says "pyspark in `[dev]`"); mypy
  `ignore_missing_imports` for `pyspark.*` (optional import).
- `scripts/ci_pure_wheel.sh`: installs pyspark in the pure-wheel venv so the distributed tests also run with
  Spark executors on the pure-Python kernel, which is exactly a Fabric Environment without the platform wheel.
- Docs: `integrations/fabric/RUNBOOK.md` (new section 5.1, parameters, troubleshooting, checklist items),
  `integrations/fabric/environment/README.md`.

### Acceptance, item by item
- *Local Spark test: the distributed bounded profile of D3 equals the single-process bounded profile within the
  T-14 bounds:* `tests/integrations/test_fabric_spark.py` (14 tests, passed). D3 (120,000 rows from the
  benchmark generator, all 10 columns) is read through Spark in 5 partitions; both sides profile the same Arrow
  table (what `df.toArrow()` returns) in bounded mode. Counts, null counts, min, max, string lengths,
  histograms: identical; mean and variance: relative 1e-9; distinct counts: both profiles within 3x the HLL
  relative error (0.81%) of the true count; quantiles: each reported value's true rank within 2x the KLL
  rank error (1%) of the requested probability; top values: `count - error <= true <= count` for every entry,
  and every value above n/64 is listed. A second test runs the executors with `SHAPE_KERNEL=python`
  (`spark.executorEnv`; I confirmed the workers really report the `python` kernel) while the driver is Rust:
  the merged result equals the Rust one on every exact field (snapshots are one format for both kernels).
- *The DM-05 notebook tests still pass:* `tests/demo/fabric/test_notebooks.py` passes. **One assertion changed
  deliberately**: `test_python_notebook_configure_and_install_cells` required the install line
  `%pip install builtin/sqllocks_shape-….whl`; it now requires the `--find-links builtin "sqllocks-shape==…"`
  form (that cell is the "Rust-kernel wheel when available" deliverable). `EXIT_KEYS` gained `kernel`, the
  notebook list gained the new notebook, and the Spark fixture sets `PYSPARK_PYTHON` (mapInArrow starts Python
  workers). Everything else in the file is untouched, and 6 tests were added for the new notebook (exit JSON,
  strict-JSON artifacts, agreement with the exact notebook, exact mode equals `shape_profile_spark`, refuses a
  contract, rejects an unknown mode, repartitioning).
- *Install cell semantics, checked locally with real wheels* (`maturin build --release` plus
  `scripts/build_pure_wheel.py`; clean venvs with only numpy, pyarrow, pandas): `pip install --no-index
  --find-links <dir> "sqllocks-shape==0.9.0"` with both wheels gives `0.9.0 rust`; with only the pure wheel
  gives `0.9.0 python`. Not checked: that a Fabric notebook's `builtin/` resolves `--find-links` the same way

- Not run: any live Fabric/Spark cluster; the CI-built manylinux_2_28 wheel (the one built here is

## PF-04 — Pipeline templates: built

Depends on PF-02 and PF-03 (both done on this branch / `build/main-plan`). Fabric: the DM-07 pipelines are
unchanged (their runbook is `integrations/fabric/RUNBOOK.md`); the *generation-then-profile* pipeline is PF-06's.

### What was built
- **Synapse** (`integrations/synapse/`, generated by `build_synapse.py`): `notebooks/shape_profile_synapse.ipynb`
  (the PF-02 PySpark notebook with Synapse auth: storage through `mssparkutils.fs`, an optional
  `linkedServiceName` that sets the Synapse linked-service token provider on the Spark session,
  `mssparkutils.notebook.exit`, `displayHTML`; `exact` mode checks a contract and diffs a baseline, `distributed`
  mode is unchecked and refuses a contract) and `pipelines/shape_gate_synapse.json` (Synapse notebook activity ->
  If Condition on the exit value -> Fail). The pipeline never passes `mode`/`partitions`, so it always gates in exact
  mode. `RUNBOOK.md` with prerequisites, steps, expected results, a [VERIFY] list and the live dry-run checklist.
- **ADF** (`integrations/adf/`): `batch/run_gate.py` (runs inside the PF-05 container: calls `shape profile`, `shape
  check`, `shape diff`, writes `gate.json`, `profile.shape`, `summary.json` to ADLS, **exits 0/1/2**, so the Custom
  activity fails on a failed gate), `build_adf.py` -> `factory/` (pipeline `shape_gate_batch`: Custom activity ->
  Lookup on `Completed` reading `gate.json` -> If Condition -> Fail; dataset `ShapeGateJson`; linked services
  `ShapeBatch`, `ShapeBatchStorage`, `ShapeAdls`, `ShapeKeyVault`, placeholders and a Key Vault secret reference,
  no secrets), `RUNBOOK.md` with the same sections. Settings travel in `activity.json` (`extendedProperties`), so no
  user value is spliced into the shell command except the image name.
- `integrations/README.md`: index of the three platform runbooks.
- Tests (in `tests/demo/fabric/`, because the `fabric-demo` job already installs jsonschema, nbformat, delta-spark,
  Java and unixODBC, which these need): `test_synapse.py` (16), `test_adf.py` (20), helper `adf_expr.py`.

### Acceptance, item by item
- *A JSON-schema-level test of each pipeline definition:* Fabric: `test_pipelines.py` (existing, DM-07). Synapse and
  ADF: `jsonschema` schemas for the pipeline, the activities (Custom, Lookup, IfCondition, Fail, SynapseNotebook),
  the dataset and the linked services. The ADF required properties come from Microsoft's published ADF resource
  schema (retrieved 2026-10-01; I read the `required` lists for Custom, Lookup, IfCondition, Fail, dependencies and
  AzureBatch; the published schema itself is too loose to validate real pipelines with, e.g. it types `command` as
  an object, so it is cited, not vendored). The Synapse notebook activity is not in that schema, so its schema is
  hand-written. Beyond structure: the activity graph and dependency conditions, that expressions reference real
  parameters and activities, that pipeline parameters equal the notebook's parameters cell, and **the gate
  expressions evaluated** (a small ADF-expression evaluator, `adf_expr.py`) on the real notebook exit values
  (Synapse, day 1 and day 2) and on the real `gate.json` documents `run_gate.py` writes (ADF: pass, violations,
  error). For ADF the script itself runs against the real Shape CLI: exit 0 (pass), 1 (violations; gate and
  artifacts still written), 1 (drift with `failOnDrift`; 0 without), 2 (missing source, missing and malformed
  contract), a 100-entry cap on a 400-violation gate, `main` reading `activity.json`; the `abfss://` path with a fake
  `adlfs`/`azure.identity` (account name, container path, the managed-identity client id, default credential
  otherwise, malformed URLs refused).
- *A runbook section per platform with a live dry-run checklist:* `integrations/synapse/RUNBOOK.md`,
  `integrations/adf/RUNBOOK.md`, plus the existing Fabric `RUNBOOK.md` (checklist updated in PF-02); a test checks
