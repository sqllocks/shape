## What was wrong

`shape_fabric.sqldb.prepare_table` committed straight after `TRUNCATE TABLE` and after
`DROP TABLE` (and after the `CREATE TABLE` that follows the drop), so a write that then failed
left the table empty (`truncate`) or freshly created and then dropped by the undo (`replace`).
`WarehouseWriter` uses the same function, and so does the `sqlserver` sink (through
`SqlDatabaseWriter`).

## Fix

`prepare_table` no longer commits a `TRUNCATE`, nor a `replace`'s `DROP TABLE` + `CREATE TABLE`
of an existing table: they commit with the rows (`db.commit()` at the end of `write_table`), or
with the first chunk under `commit_rows`, and a failure rolls them back with the rows. A table
that did not exist is still created and committed on its own, as before, so every `create` /
`append` tape stays byte-identical. `prepare_table` now returns whether it committed a new
table; for a replaced table it returns `False`, so `undo` never drops the old table that the
rollback brought back.

Other SQL writers checked:

- `shape_databases` PostgreSQL: already one transaction (PostgreSQL DDL is transactional); no
  commit between the drop/truncate and the rows. Not affected.
- `shape_databases` MySQL: MySQL itself commits implicitly at every DDL statement
  (`TRUNCATE`, `DROP`, `CREATE`), so the writer cannot roll them back; this is documented in
  `mysql.py` and the plugin README and is not the #429 defect (the writer does not commit early;
  the server does). Not changed.

plugins/shape-fabric/tests/fixtures` (never edited by hand). Before writing into `fixtures/`
the same command was run into a scratch folder and every file compared byte for byte:

- `sql_replace_with_key.json`: re-recorded; the two `commit` steps after `DROP TABLE` and after
  the `CREATE TABLE` that replaces it are gone (the drop now commits with the rows).
- new scenarios `sql_truncate_that_fails_keeps_the_old_rows` and
  `sql_replace_that_fails_keeps_the_old_rows`: a `truncate` / `replace` whose input fails after
  the first batch went in; the tape pins `rollback` with no commit before it, and a
  `SELECT COUNT(*)` afterwards answers 3 (the old rows).
- every other tape (30 files) byte-identical.
