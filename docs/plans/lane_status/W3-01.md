## Decisions I made where the issue was silent (all documented in `docs/RULES_TESTING.md`)

* **A rule that already fails on the unmutated data cannot kill a mutant** (it would "catch" every
  mutant). It is listed in `baseline_failed_rules` and left out of `rules_killed_none`. Found by
  running the worked example: a contract that failed on the clean data scored 100%.
* **Entry status.** `fail` if a measured rule fails; `pass` only if every declared rule was measured
  and passed; otherwise `not_measured`. So a partly measured version is never reported as a pass.
* **Windows** are ISO weeks and calendar months; a window with one version is still merged, so a
  rule is measured the same way in every window. An incident is "inside" a window when the dates
  of its versions overlap it. `--since/--until` apply before grouping.
* **What a merge or a share-safe form leaves unmeasured:** whole-data rules (`pattern`,
  `distribution`, `allowed_values`, true rates, `no_placeholder`, joint rules) in a merged profile;
  everything the safe form does not store (`unique`, `min`, `max`, `nullable`, ...) in a safe form.
  The share-safe form cannot be merged, so a week or month holding one is `not_measured` with a reason.
* `shape rules mutate` exits 2 when no mutant changes a cell (nothing to corrupt). `--min-score`
  outside 0 to 1 is exit 2.
* Report fields beyond the issue's list: `status` per mutant (`killed`/`survived`/`not_applicable`),
  `baseline_failed_rules`, `diff`, per-entry `rules` counts and `first_date`/`last_date`.
* The module of the backtest is `shape.rules.history` (not `backtest`) so the name `backtest` is the
  function in `shape.rules`.
* Observation, not a defect of this package: `type_change` (a column delivered as text of numbers)
  does not change the profile's inferred `dtype`, so a `dtype` rule does not kill it; `min` did.
