## Changes outside the new package

- `src/shape/schemacheck.py`: learned `maximum`, `pattern` (a search, as in JSON Schema) and `not`.
  The issue requires the emitted schema to be validated with `shape.schemacheck` and to reject a
  row that breaks a range or a pattern, which the checker could not do. Test:
  `tests/contracts/emit/test_schemacheck_keywords.py`. Other keywords are still ignored, as before.
- `src/shape/cli/main.py`: registers and dispatches the `contract` command.

## Decisions recorded (inside the Wanted list, nothing added)

- A contract `pattern` is a profiler label; the regular expression behind each label is in
  `_common.PATTERNS`. The profile gives the label at 90% of a sample, the emitted JSON Schema,
  pandera and database check apply it to every row; GX keeps 90% with `mostly`. Documented.
- `ddl`: `pattern` is a CHECK on PostgreSQL (`~`) and MySQL (`REGEXP`), not expressible on T-SQL and
  Fabric. Fabric Warehouse has no CHECK constraint, so `min`/`max`/`allowed_values` are listed there.
- `jsonschema` and `gx` emit one table: a `tables` contract needs `--table` (exit 2 otherwise);
  `ddl` and `pandera` emit every table.
- pandera: a nullable integer is `"Int64"` and a nullable boolean `"boolean"` (numpy types cannot
  hold a null), so a frame with plain `int64` for a column that may be null fails the dtype check.
- `required_columns` maps to `required`, as the issue says; a column listed but not required is
  optional in the emitted schema and suite, while `shape check` reports it missing. Documented.
- GX: `allow_extra_columns: false` uses `expect_table_columns_to_match_set`, one expectation beyond
  the issue's list (it is the dbt emitter's mapping); `dtype` is not expressible (backend-specific).
- `None` in `allowed_values` is dropped from the normal form (`nullable` decides about nulls).
