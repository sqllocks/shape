## What was built

- **Three domains in `plugins/shape-domains`**, entry points `shape.domains: healthcare | hr | insurance`
  (`pyproject.toml`, three additive lines), modules `healthcare.py`, `hr.py`, `insurance.py` on the shared
  `PackagedDomain` loader, each with `data/<domain>/schema.json` (3nf), `schema_star.json` and `reference/*.arrow`.
  Schemas are the baseline's dumps in `benchmarks/vs_refengine/fixtures/schemas/` imported by P4-01a's importer, with
  the same `unit: ns` rule as P6-01a. Reference data is every file of the baseline domain's `reference_data/`

  position_titles, training_courses; insurance: claim_categories, peril_types, policy_types). The ZIP locations
  that healthcare reads from its own folder and insurance from the baseline's shared folder are byte-identical to
  retail's file (`cmp`), so both **borrow retail's `us_zip_locations`** (as financial does) instead of copying 3 MB.
- **`export_domains.py`**: three entries added to `DOMAINS` (additive); `--check` exits 0 and `export_retail.py
  --check` exits 0.
- **D-10 notice:** `THIRD_PARTY_NOTICES.md` names the three domains in the existing MIT notice (same copyright
  holder); no new text.
- **Engine/strategies: no change was needed.** Everything the three schemas use already exists.
- **Harness: one edit** (`domain_1to1/verify.py`, `Pools.faker`): the pool of the `sentence` provider is the baseline's

  so there is no allow-list entry.

- **Tests:** `tests/generation/test_domains_p601b.py` (41 tests, both kernels): discovery and `kit.check_domain`, the

### 2. GEN-IN >= 10x at medium: not met for any of the three

T-19 method: `domain_1to1/bench.py --impl shape --domain D --scales medium --runs 5 --warmup 1`: one discarded

each run waits for a 1-minute load average <= 1.5 (the loads shown are what it saw). Timed region: load the domain, build the

(The txt reports list the same runs at two decimals; the json keeps full precision: medians 2.512/0.356,
0.225/0.085, 0.548/0.093, i.e. 7.06x, 2.65x, 5.92x. Reports: `bench_gen_in_{domain}.{json,txt}`; machine in
`meta`.) Warm-up runs are in the txt. Load before runs was 1.17-1.47 (under the 1.5 gate, partly from the benchmark's own
previous process).

Nothing here is domain-specific, as far as I can measure:

- Fixed costs per domain are small: loading the domain 5-9 ms and building the engine 1-2 ms (`load_domain`,
  `Engine`), for the three domains.
- hr (78k rows) and insurance (213k) are tiny workloads. Their Shape time is 60-100 ms of which generation is
  about 40 and 55 ms: the first level of tables (tiny reference-like tables) already costs 8-14 ms, which is the
  engine's first-allocation stall that P6-01a's Escalation 2 describes. 10x for hr would be 23 ms in total, including
  writing nine Parquet files, and for insurance 55 ms. P6-01a's analysis (CPU-bound, allocator, single-file Parquet
  encoding) applies here without change.
- healthcare: 1.26 M rows in 0.36 s. Single-threaded column times (instrumented `Engine._column`): the top items are
  `lookup`, `record_field`, `foreign_key` gathers of the 270k/356k-row child tables (`medication.patient_id` 44 ms,
  `diagnosis.description` 38 ms, `claim_line.procedure_id` 34 ms); all engine strategies. No domain schema choice
  stands out, and the equivalence constraints fix what each column must produce.

Per the lane's instructions the engine-wide work (allocator, native generation path, parallel Parquet) is the
round-2 lane on `lane/P6-01a`; I did not duplicate it, and I made no domain-specific change to the timing.
