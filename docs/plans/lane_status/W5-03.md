2. **`shape init` does not add `*.shapevault` to `.gitignore`.** `shape init` is W1-04 (not merged).
   `shape git-setup` does it (tested). One line in W1-04's init once both are integrated.
3. **`shape generate` has no run manifest in this tree** (the run manifest of `shape.scenario` is
   written by scenario runs). The vault run records `generation_mode`, `vault_id` and
   `vaulted_columns` in the command's `--json` result and in the run metrics file
   (`--metrics RUN.json`). If a manifest for `generate` lands later, it takes the same three fields.
4. **Interpretation of "only values that the safe capture suppressed".** A column's vault entry is
   the column's complete category table (`enum_values`, `value_counts_ext`) when the safe capture
   suppressed or folded any of it, not only the withheld rows: generation then draws from one table
   whose frequencies add up (the released categories are public and the file is encrypted). A
   column that was released in full gets no entry. If you want only the withheld rows, `build._categories`
   is the one place to change, and the generation overlay would then merge them with the profile's.
5. **Pre-existing defect, not mine, not fixed:** on `build/main-plan` (checked in a clean worktree)
   `shape generate --from X.shape -f csv -o DIR` writes **no file** (while printing "Wrote 1 csv
   files") when the fitted schema has a copula pair (two correlated numeric columns): `needs_post_pass`
   is true and `_write_overlapped` writes nothing. My generation tests use a dataset without such a
   pair. The summary format (`-f summary`) is not affected. It is outside this package.

## Security review

Standard primitives only: AES-256-GCM through `cryptography`'s `AESGCM` (via `shape.security.crypto`),
`os.urandom` for keys, nonces and ids. No custom cryptography; `shape.vault` imports primitives only
from `cryptography` and `shape.security.crypto`. Bandit is clean on the new files (`-ll` as in CI, and
the three low-severity findings on the one `git` subprocess carry `nosec` with the reason).

**Every key path**

| Key | Where it comes from | Where it lives | Where it goes | Never |
|---|---|---|---|---|
| KEK, creation | `kek.write_kek`: `os.urandom(32)`, base64 | a file created with `O_EXCL` and mode 0600 (POSIX); never overwritten | the file only; `keygen` prints the 16-hex key id | printed, logged, returned in JSON |
| KEK, use | `--kek REF` or `kek=`: `env://NAME`, `file://PATH`, a path, `kv://` through `credrefs.resolve_reference`; a group- or world-readable file is refused | a `bytes` local in `resolve_kek`, passed to `seal_vault`, `open_vault`, `verify_vault`, `rekey` | `AESGCM` as key; its SHA-256 prefix (`kek_id`) is written to the vault and named in errors | accepted as a literal command-line value (a literal is refused and not echoed); in a message, a log, `--json`, or a vault |
| Data key | `os.urandom(32)` in `seal_vault`, fresh per write | a local variable for the length of the call | encrypted under the KEK into `wrapped_key` | written or returned in the clear; reused (tested: two writes share none) |
| Data key, opening | `decrypt_aes_gcm(wrapped_key, KEK)` in `open_vault` | a local variable | `AESGCM` as key for the columns | kept after `open_vault` returns |
| New KEK and new data key | `rekey`: `--new-kek REF`, a fresh data key | locals | as above | the old data key is not reused |
| Decrypted values | `open_vault` payloads | `OpenedVault` / `VaultRun` in memory | the schema document of a vault run, then the generated data (real values: one stderr warning, `generation_mode: "shape+vault"`) | the vault, the profile, the plan, `--json` (it names columns, ids and counts only), stderr or an error |
| Signing key (`rekey --key`) | the existing `shape.artifact.keys` loader and passphrase rules | unchanged | `sign_artifact` | changed by this package |

Messages carry column names, policies, ids and the 16-hex key ids only (metadata in the clear, listed
as residual risk V3). Temporary files (`ops.write_file`) hold ciphertext only, in the target's
directory, mode 0600, and are removed on failure. A KEK held in an environment variable is as exposed
as the process environment (residual risk V6). Python cannot erase key bytes from memory; documented.

Reviewed and rejected: a passphrase-derived KEK (out of scope), reading the KEK from a literal
(refused), logging `kek_id` of a *file path* (paths are named, keys never), `--json` echoing a
payload (no command does).
