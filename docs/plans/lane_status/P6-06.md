## `transform star` and `generate --mode star`: shared code?

No. `generate --mode star` selects a domain's *generation schema* (P4-10's `schema_star.json`, whose table list
is the same nine retail tables) and decides what values to generate; `transform star` reshapes tables that
already exist (joins, surrogate keys, date dimension). There is nothing to share beyond the retail data itself.
The two are cross-referenced in `docs/TRANSFORMS.md`.

## Deliberate differences (narrow, named, each with a test)

The harness lists these (`compare.DIFFERENCES`) and matches each only in its exact pattern.

| Name | Reason |
|---|---|
| `nullable_int_float` | The baseline's dataframe turns an integer column with nulls into `double` (`5` -> `5.0`), in the star tables and in the CDM `dataType`. Shape keeps `int64` with nulls. Values compared as numbers. (Not a baseline decision; a library artefact.) |
| `date_dimension_covers_all_facts` | **Baseline defect, fixed (owner's standing decision, 2026-10-01).** It builds `dim_date` from the date columns of each fact's *primary* table before joins. `fact_sale`'s `order_date` arrives through the join with `order`, so it is never collected: `dim_date` covers only `return_date`, and `fact_sale.sk_date` points at dates with no row (measured here: 28 of 12,500 rows with Shape's data, 21 with the baseline's). Shape builds `dim_date` from every fact's `sk_date`: 1,468 days against 1,400, a superset, rows inside the baseline's range equal, 0 uncovered. Test `test_fix_dates_that_arrive_through_a_join...`; the harness asserts 0 uncovered. |
| `model_wording` | `model.json`'s description, application and `modifiedTime` name the tool or the run time; Shape's wording is used, the time ignored. (Default model name is `Shape<Domain>`.) |

### Other baseline defects found and fixed (each has a regression test; none changes retail's output)

Silent behaviours that corrupt or hide errors become errors (a map that is wrong should not "work"):

- A dimension or fact whose source table is missing produced an empty table silently -> error.
- A join (or enrichment) naming a missing table or key column was skipped silently -> error.
- A foreign-key column that is not in the table was skipped silently -> error. **The baseline's own retail map
  contained one** (`fact_return` mapped `product_id`, which neither `return` nor `order` has); Shape's retail
  map drops that entry, so the output is unchanged.
- A fact join to a table whose key is not unique repeated the fact rows (double-counted measures) -> error.
- Several foreign-key columns mapped to one dimension wrote one `sk_` column, the last silently winning -> error
  at map load.
- Several `date_columns` on one fact wrote one `sk_date`, the last silently winning -> each gets
  `sk_date_<column>` (one date column: `sk_date`, as the baseline).
- A date span over 60 years was silently cut to 60 years, leaving fact dates without a `dim_date` row -> error.
- Misspelled names in `include` were dropped silently -> error (`columns`).
- Dimension enrichment with colliding column names was renamed `_x`/`_y` by the dataframe library -> error
  asking for a prefix.
- Two tables that map to one CDM entity wrote both to one folder, the second over the first, and listed both in
  `model.json` -> error before anything is written.
- The orphan-FK warning counted null keys ("no promotion") as orphans (8,673 "orphans" on the small retail, all
  nulls); Shape reports only non-null keys with no dimension row.
- CDM type labels followed the pandas dtype and, for text, a `*_date` name heuristic; Shape maps the Arrow type
  (date -> `date`, timestamp -> `dateTime`, decimal -> `decimal`, time -> `time`; text stays `string` whatever
  its name). Identical on retail.
- Text date columns that cannot be parsed were silently null (`errors="coerce"`) -> error. Null keys never join
  (the baseline's dataframe joins null to null).

These are reachable only with a map or input the retail harness does not use, so the harness cannot show a
difference for them; the unit tests do.
