## Decisions and ambiguities (lead: please confirm or correct)

1. **"`shape profile` text output and `shape show` print the new fields".** `shape profile` prints JSON
   (`written`, id) and writes `--html` and `--json` files; there is no text column table. `shape show`
   and `shape cat` already print every profile field. I added the fields to the `--html` report cards
   (`describe()` lines). I first added them to `Profile.summary()` (so `--json` carried them) but
   `tests/demo/core/test_profile.py::test_summary_single_table` pins that key set, so I reverted it. If
   you want a text table or a flag, that is a new command surface and needs a decision.
2. **Sample caps are 50,000 (heaping, Benford, tail) and 10,000 (model selection)**, under the issue's
   100,000 ceiling, because every numeric column pays for them on every profile (see cost).
   The sample is stratified: the column is cut into `cap` runs of consecutive rows and one row is drawn
   from each with `default_rng(42)` (equal inclusion probability, deterministic, cheaper than a
   without-replacement draw).
3. **Noise guards on the diff kinds** (documented in `docs/DRIFT.md`): `benford_change` needs the MAD to
   rise by more than 3 standard errors of the difference, `tail_change` the alpha drop to beat 3 standard
   errors, `zero_inflation_change` and `heaping_change` a share/ratio move beyond 4 standard errors. The
   spec's thresholds are necessary, not sufficient. Found by `tests/diff/test_drift_engine.py::
   test_two_samples_of_one_distribution_do_not_drift`: lognormal(3, 0.8) has a MAD on a class edge and
   two samples of 1,500 landed two classes apart. The guards are what keep the sweep's false-positive
   bound unchanged; a regression test pins the case.
4. Heaping choices the issue leaves open: zeros are excluded; a unit needs at least 20 grid points and
   two multiples in range; the reported unit is the one with the largest excess share among those that
   satisfy the flag (ties to the larger unit); `heaped` and `resolution` sit inside the `heaping` object.
   Benford "positive" means every value is positive. Minimum sample for items 1 to 3 is 20 finite values.
5. The new fields are registered in the generation plan as "not modelled" (`generation/fit.py`,
   `learn.py`): generation does not use them (out of scope).
6. Registry `diff` between a profile stored before this change and a new one lists the new fields as
   changed (same as when `placeholders` and `joint` were added).

## Cost (for the lead: T-19 / G1)

Per numeric column about 16 ms CPU (2M-row column; 5 ms of it is the full-column scan). Measured on this
4-core machine with the Rust kernel, best of 3, same table, base tree vs this branch: an 8-numeric-column
2M-row table profiles in 0.96 to 1.03 s on the base and 1.15 to 1.28 s here, i.e. **about +20%**. The
pinned benchmark gate (`bench.py`, 10% limit, nightly reference) was **not run** (about 45 min with a
lock; the machine was shared with test runs). Expect the profile benchmarks to show this cost. Options if
it is not acceptable: an opt-out switch, smaller caps, or moving the fits into the Rust kernel; each is a
decision for you. The 10M-row test bounds time and memory but does not enforce the +20% figure.
