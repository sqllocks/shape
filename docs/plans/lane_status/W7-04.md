## Decisions I made where the issue is silent or contradicts itself (please review)

1. **`source` means three things in the issue.** Item 4 gives `diff`, `check`, `verify` and `profile`
   a `source` that names a project source; item 8 gives `verify` a `source` that is the real data;
   `profile` already has `source` (the data path). One name cannot be both on `verify`. I kept the
   CLI's meaning: `verify.source` is the real data (`shape verify --source DATA`); `diff.source` and
   `check.source` are project source names; `profile.source` and `verify.path` may *name* a project
   source instead of a path when a `project` is given (an existing path wins), which is what
   `shape profile orders` and `shape verify orders` do. A source for `verify` is otherwise the
   project's single source, as on the command line. I did not make `path` optional.
2. **`diff`/`check` keep `before`, `after` and `contract` required.** Making them optional (so the
   project supplies the baseline or contract) would change a 1.0 required argument, which the 1.0
   promise forbids; a 1.0 request without it must stay `usage.missing_argument`. So there is no
   baseline lookup in the bridge `diff`. The `project` block therefore has no `baseline`.
3. **`proposals_list` evidence.** I read "evidence that carries values ... is `null` with
   `"redacted": true`" as: the *values inside* the evidence are `null` (`range.child`,
   `range.parent`, and any other list of plain values, wherever it sits) and the proposal carries
   `"redacted": true`; names, counts, fractions and verdicts stay. A decision file does not say which
   columns are classified (no profile is given), so the values are withheld for every relationship
   whatever the column.
4. **`verify` under a project**: `passed` stays the 1.0 result (all gates, and `strict`), and
   `enforced_passed`, per-gate `mode` and the `project` block are added, as `verify -o x.json` does.
   The exit code of the CLI follows `enforced_passed`.
5. **Gate `details`**: the memorization and utility gates' details are counts, distances and scores;
   the range gate's `actual_min` / `actual_max` are data values and are dropped. The *error messages*
   of the range gate still say "(actual min: ...)": those are 1.0 messages and unchanged.
6. **`project_validate`** returns `valid: false` with problems for every content problem, but a file
   of a *newer* version is the error `input.unsupported_format_version` (the CLI prints it as
   invalid). `line` is read from the YAML error text ("line N"), `path` is the key path or
   `document`.
7. **`design`** with lint errors is a successful response with `passed: false`, `tables: null`,
   `ddl: null` (the CLI prints the findings and writes no DDL). `design` has no `strict`.
8. **`format_schema`** `format` is `null` for documents that identify themselves by their version
   only (generation schema, model v1/v2, profile engine); names: `design-input`, `generation-schema`,
   `decisions`, `project`, `model`, `model-v1`, `model-v1-ga`, `profile-engine`.
9. **`contract_validate`** lists every problem (each with a `location`), not only the first, and also
   returns `kind: "check-contract"` and `warnings: []`; the 1.0 `validate` (a different contract,
   `name` and `fields`) is unchanged. Text that is not JSON is `valid: false`.
10. **`safe_scan`** rebuilds each finding's message from its rule (the engine's detail holds the
    value); a pointer is scrubbed with the scanner's own personal-data patterns, which cannot catch
    an arbitrary non-pattern value used as a dictionary key.
11. **`effects`** are static per command (what it can do), e.g. `generate` lists `writes_files`
    although it writes only with a `format`. `sink_config` holds paths in an object and cannot carry
    `x-path`; the commands that take it list `writes_files` and `network`.
12. `warning()` now refuses a code that is not in `WARNING_CODES` (as `BridgeError` does for errors);
    the eight 1.0 codes are registered and published in `index.json`, plus the new
    `project_source_not_selected`.

## For the lead

* **Integration clash between W1-03 and W1-04 (not mine, found while testing).** With both merged,
  `shape verify DATA --source REAL` exits 2 with "no shape.yml found from ... upwards: --source needs
  one": `shape.cli.project.context()` reads `a.source` as a project source name, but on `verify`
  `--source` is the real data. `tests/bridge/test_verify_1_1.py` works around it in an autouse
  fixture so the CLI can be the reference. A fix for W1-04 (I may not change the CLI here):
  ```diff
  --- a/src/shape/cli/project.py
  +++ b/src/shape/cli/project.py
  @@ def context(a: argparse.Namespace, hint: str | None = None) -> Context | None:
  -    named = getattr(a, "source", None)
  +    named = None if getattr(a, "cmd", None) == "verify" else getattr(a, "source", None)
  ```
  The bridge has no such clash (`verify` never reads `source` as a name).
* **Project gate names**: `shape.yml` validates `gates:` against `GateRunner.available_gates()`,
  which does not list `memorization` or `utility`, so a project cannot make them `observe`; they are
  always enforced. Say if W1-04 should add them.
* **Existing tests I had to edit** (the issue says they pass unchanged; these assert things that are
  true only for a 1.0-only bridge): `tests/bridge/test_protocol.py` (`"1.0 to 1.0"` is now
  `"1.0 to 1.1"`, which the issue itself specifies); `tests/bridge/test_schemas.py` (the command set
  gains `ADDED_1_1`, and the sample request for a required enum argument uses a valid value);
  `tests/bridge/bridge_helpers.py` and `conftest.py` (a `Caller11` and an `api11` fixture; `Caller`
  behaves as before); `tests/bridge/make_vectors.py` and `vectors_lib.py` (vector cases declare the
  version of their command; two volatile keys). Nothing was skipped, xfailed or loosened. The
  regenerated top-level vectors differ from the 1.0 ones only in `api_version` and the added cases
  (the 1.0 copies are in `vectors/1.0/`, unchanged).
* **`.github/workflows/*`: no change needed.** CI's `pip install -e '.[dev,...]'` already carries
  PyYAML (`dev` lists it) and scikit-learn comes with the `advanced` extra the main job installs.
* **AUD-bridge merge**: additions are in new modules; the files both may touch are `protocol.py`,
  `spec.py`, `core.py`, `context.py`, `schemas.py`, `registry.py` and `docs/BRIDGE.md`. After merging,
  run `shape bridge schema --out docs/bridge/schema` and `python tests/bridge/make_vectors.py` and
  review the diff (only additions are expected), then `pytest tests/bridge`.
