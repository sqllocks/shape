## Blocking question: signed bytes in T-SQL

Wanted item 1 requires signed Arrow `int8` to become T-SQL `TINYINT` while item 3
requires faithful round trips and common acceptance requires negative/boundary cases.
Arrow signed `int8` includes `-128` through `127`; SQL Server `TINYINT` supports only
`0` through `255`. Mapping `-128` or `-1` to that type cannot preserve the value.
Fabric Warehouse's T-SQL mapping needs the same decision.

Evidence run in this session with PyArrow and the current map:

```text
Arrow signed int8 boundaries: [-128, -1, 0, 127]
Current tsql map: BIGINT
Wanted T-SQL TINYINT range: 0..255; -128 and -1 cannot be represented
```

Question: May the T-SQL and Fabric maps use `SMALLINT` for signed `int8`?

Options:

- Use `SMALLINT` for signed `int8`, preserving every negative and boundary value.
- Keep `TINYINT`, but refuse negative values; this changes the fidelity requirement.
- Keep a wider legacy type; this changes the specified width mapping.

Recommendation: approve `SMALLINT` for signed `int8`; make no unilateral exception.

## Separate clarification: time-zone identity

Wanted items 1 and 3 require MySQL `TIMESTAMP` with session zone UTC, and a zoned
value reading back equal to the microsecond “with its zone.” MySQL `TIMESTAMP`
stores an instant and converts it through the session zone; it does not store the
original named zone. PostgreSQL `TIMESTAMPTZ` likewise does not retain an original
IANA zone name. Offset preservation and original named-zone preservation are
separate guarantees.

Question: Does “with its zone” mean preserving the instant and returning an aware
UTC value, or preserving the original named zone/offset?

Options:

- Preserve the instant to the microsecond, return aware UTC where supported, and
  document named-zone normalization.
- Preserve the original zone separately, requiring a companion column or metadata
  outside the currently specified single-column mapping.

Recommendation: approve instant preservation with documented UTC normalization.
