How it works: events reach the tee after the sink delivered them; per table, a worker thread feeds
the **stream profiler** (`GlobalProfiler`, bounded mode, the engine behind `shape stream-profile`)
and score accumulators (running moments, a value sample for the KS statistic, distinct values,
value counts), and compares them with the target. The target is reference data: a file or directory
as `shape fidelity` reads it, or a domain or schema from which a reference is generated
(`--live-target-seed`, default stream seed + 1). Alerts: `score-low`, `score-drop`, `column-low`
(opt-in), `live-error`, `recovered`; edge-triggered; to stderr, to `--live-alerts FILE` as JSON
lines (`shape-live-alert-v1`) and in `--live-report`. Exit codes: 0 (alerts do not change it),
`--live-fail` gives 1 when a live pass mark is missed at the end or a non-score error alert is
active, 2 for bad input. All in `docs/EMIT.md`.

Exact where it can be, bounded past the caps (documented, and listed under `approximate` in the
report): moments and null rate exact; KS values and distinct values exact up to `--live-sample`
(100,000 per numeric column, then a reservoir sample) and `--live-key-cap` (250,000, then the
profiler's HyperLogLog); text value counts exact up to the key cap, then the profiler's top-500.

### 3. Overhead measured

Same harness, retail medium (1,965,400 events), median of three interleaved runs, the P5-01
runtime with default settings. Machine: 4 cores, shared with the generator's threads.

| sink | no tee | tee (score only) | tee + stream profiler |
|---|---|---|---|
| file (JSON lines), `--no-realtime` | 113,909 events/s | 81,680 (-28.3%) | 71,725 (-37.0%) |
| null sink, `--no-realtime` (generator ceiling) | 1,758,349 | 387,608 (-78.0%) | 215,342 (-87.8%) |

The tee is **not small in bulk mode**: the live side is CPU work (about 1.5 us per event measured
alone, 3 us with the profiler), done on a thread that shares the interpreter and the cores with the
generator and the sink, so a free-running emit loses 28% to 37% of its throughput against a file
sink. The paced case it is made for is cheap: at 10,000 events/s (`--realtime`, 20 s each) the rate
holds with the tee and the worst whole second is 0.5% off the target in all three modes:

| mode | rate | worst second | max lag | CPU |
|---|---|---|---|---|
| no tee | 10,000.6 (+0.006%) | 0.5% | 53 ms | 25% of a core |
| tee | 10,000.2 (+0.002%) | 0.5% | 6 ms | 43% of a core |
| tee + profiler | 9,999.4 (-0.006%) | 0.5% | 35 ms | 46% of a core |

(`--no-live-profile` drops the profiler: the profile costs about 1.6 us per event.) The report's
`observe_seconds` and `docs/EMIT.md` give the same figures a user can check. Choices that kept it
down: the tee runs on its own thread behind a 256-batch queue (a stall, such as a scoring pass,
does not stall the paced delivery; when the queue is full delivery slows and nothing is skipped);
events are gathered into chunks of 8,192 per table before they are counted; a table is re-scored
only when it changed; the reference's KS values are thinned to 200,000 order statistics (an error of
5e-5 points). I stopped here rather than go further: the remaining cost is per-value work in
pyarrow and numpy, which is the Rust-kernel step of plan section 4.2 if the bulk figure has to
come down. The plan sets no overhead gate for P5-03.

## Decisions and limits (for the lead)

* **The target must be data.** A `.shape` profile (sketches) does not hold the distributions the
  score needs (KS, value overlap), so a profile is not accepted as a target; a domain or schema is
  (a reference is generated), and so is a file or directory of tables. This is how I read "the
  target shape the events were generated from" given the acceptance ("within 0.5 points of
  `shape fidelity`", which needs reference data). If a profile target is wanted, it is a lower-fidelity
  scorer and a new decision.
* **Alerts are gated by progress** (`--live-min-progress`, default 0.5; and `--live-min-events`),
  because a half-emitted table scores lower than the finished one (distinct counts grow with the
  rows; seen on `order`: 77 at 4,400 events, 95.6 complete). The score itself is never gated. The
  overall is judged only when every table is, because the mean of a few tables is not the overall.
  Tables are streamed one after another, so the overall alert is late in a run; per-table alerts are
  the live signal.
* **Past `--live-key-cap`, text columns are approximate**: overlap and chi-squared then use the
  profiler's top-500 values, which can move such a column's score by many points (the unit test shows
  a 15,000-category column is flagged, not claimed exact). Numeric columns past the caps stay within
  0.04 points in the runs above.
* **A resumed run** scores only the events it delivered (the live state is not checkpointed).
* A numeric live column against a categorical target column (a type change) scores the categorical
  branch with no keys; not exercised by any workload.
* Bulk-mode overhead is large (above); at realistic paced rates it is not.
