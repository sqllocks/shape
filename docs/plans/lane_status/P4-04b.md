* **(b) null rate** within max(5 sigma, 1.5 x the baseline's seed-to-seed drift): every case
  (`compare._null_rate`, `parts.check_series`), including nullable `native/first_name_nullable` (20%).
* **(c) numeric and datetime KS** <= max(critical value at alpha = 0.001, 1.5 x the baseline's
  largest seed-to-seed KS + 0.002): all `formula/*` cases (8), all `derived/*` cases (the day offset
  added to a date, 9), the `computed/*` aggregates (6).
* **(d) low-cardinality categorical TVD** <= max(3 x multinomial noise, 1.5 x seed-to-seed TVD + 0.002)
  and vocabulary overlap >= 0.999: `native|faker/state_abbr` and `/city`, the integer-valued
  offsets and counts (value counts), and string lengths of every text case.
* **(e) pooled high-cardinality strings**: `parts.parts_fingerprint` parses every value into its
  components by regular expression; each pool component must be a member of the pool (>= 0.999;

  the sha256 of each pool file with the digest `baseline_p404b.py` writes into the fixtures, and
  `export_pools.py --check` compares each file with the baseline's tuple.
* **Negative controls** (`test_the_comparison_can_fail`): another provider's text, a formula off by

## Decisions I made inside the work package, and things to confirm

1. **Clause-exact comparison instead of `compare.check` for these cases.** `compare.check`
   (P4-04a) adds checks that are not T-21 clauses: a duplicate-rate check, and a character-class
   check at *every position*. Applied to variable-length pooled text they produce false failures
   that no tolerance should absorb: at the last positions of an e-mail or a name only a few baseline
   values exist, so a perfectly equivalent Shape column has none there (TVD 1.0); and for 12 independent
   positions of `pystr`, `3 x noise` is only about 2.4 sigma, so the chance that one of 12 positions
   fails is about 17%. `parts.check_series` implements exactly (b), (c), (d) with `compare`'s own
   tolerance code (`_null_rate`, `ks_grids`, `CRIT_001`, `_categorical`), and `parts.check_parts`
   implements (e) at component level as T-21 (e) asks. No tolerance was touched. If the lead
   wants the stricter P4-04a comparison for text anyway, it fails only on the sampling artefacts above.
2. **Pool files live in core (`src/shape/builtins/strategies/pools/`), not in `shape-domains`**
   (D-10 says "copy the pools into `shape-domains`"). The `native`/`faker` built-ins need them, and
   a built-in cannot depend on a plugin distribution. Total 284 KB, loaded lazily per pool.
   `shape-domains` can ship its larger domain data separately. The data file header names its origin
   as the US Census via Faker's en_US provider plus generated entries; `THIRD_PARTY_NOTICES.md` was
   not edited (the owner is to confirm the copyright question, section 9).
3. **`faker` with an exotic provider cannot be compared to the baseline here**: the pinned baseline
   venv (section 1.2) does not install `faker`, so the baseline's own pool-and-sample path cannot run
   (it raises `ImportError`). It is covered by contract tests with a stub `faker` module (pool size
   cap, row addressing, args, locale, mixed types, missing package) and the 15 built-in providers by
   the equivalence tests above.
4. **`computed` dtype.** The baseline's `computed` column is an integer only when every parent has a
   child; otherwise a pandas NaN makes it float (then `fillna(0)`). Shape always returns the natural
   type (integer for counts and sums of integers). The equivalence cases for `count_children` and
   `sum_children` of an integer column therefore use 25 children per parent (a parent without children
   has probability e^-25), so both implementations give integers; a sparse case is tested separately
   (`test_computed_parents_without_children_get_zero_of_the_natural_type`).
5. **`lookup_parent` is unreachable in the baseline's generator** (`apply_compute_phase` looks for a
   foreign key in the *other* table pointing at this one, which a `lookup_parent` column never has).
   Shape's compute phase implements the rule; tested by value (`test_computed_lookup_parent_copies_the_parents_value`),
   not against the baseline.
6. **`derived` is compared by the quantity it adds.** The date source of the baseline is its
   `temporal` strategy (another work package in Shape), so the test compares the whole-day offset
   (target minus source) between the two, and generates Shape's source with a small stand-in strategy
   (`test_dates`); the cross-table case likewise uses a stand-in `foreign_key`-free key (sequences
   with 10,000 unmatched child rows). The stand-ins are test-local (`Engine(strategies=...)`); they
   win over any registered strategy of the same name, so the sibling lanes do not affect these tests.
7. **`formula` is stricter than the baseline's `eval` on purpose**: no attribute access, calls,
   text or indexing; a null input gives a null (the baseline raises on `None`); text columns are an
   error. It accepts more numeric syntax than the baseline (`min`/`max`/`round` of arrays, which the
   baseline cannot evaluate).
8. **`derived` cross-table generates the parent table in full once** (`Engine.generate_table`,
   memoised) and reads it by key: arithmetic when the parent's key is a `sequence`, a hash lookup
   otherwise. Fine at the scales of the equivalence runs; memory is the parent table.
9. **Test edit outside my files**: `tests/benchmarks/test_engine_plan.py::test_dry_run_plans_retail_without_strategies`
   assumed `faker` is not registered (P4-03's lane had changed the assumed-missing name from
   `weighted_enum` to `faker`). It now names a strategy no plugin provides, so no later work package breaks it.
   Sibling lanes that change the same line will conflict trivially.
