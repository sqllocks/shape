## What was measured first (T-28 style stage split and counters)
d1.csv is 200k rows x 6 columns (3 int, 2 text, 1 float), 7.7 MB. On this VM (same single-thread speed as the lead's:
Shape 1 thread 0.17 s here, 0.17 s there) before any change:

- Stage split of one multi-thread call (0.09 to 0.20 s): `load_columns` (pyarrow CSV read) 0.025 to 0.12 s, column pool
  0.065 to 0.075 s, correlation 0.01 to 0.03 s on its own thread, `table_to_dict` under 1 ms.
- **The variance is the read, and it is system time, not parsing.** The timed region costs 0.13 to 0.17 s of user CPU but
  0.04 to 0.29 s of system CPU for about 15,000 page faults (4 to 17 microseconds each on this VM class); a single
  `pyarrow.csv.read_csv` of the file ranged 0.025 to 0.13 s between fresh processes with 0.004 to 0.116 s of that in the
  kernel. The file is read as one 16 MiB block, so one thread parses it and one 8 MB buffer is allocated cold.
- **The column pool does not scale as it should:** serial column times sum to 0.11 s, the pool took 0.065 s, not 0.03 s.
  Cause 1 (scheduling): `_col_cost` puts every int and text column in one tier, so `email` (the longest column, 0.04 s)
  was queued behind the cheap int columns, started in the second wave and ended the pool at about 0.06 s.
  Cause 2 (GIL-free kernel calls plus page-fault contention): in the pool `email` took 0.055 s against 0.039 s alone.
- **Pure waste found by cProfile:** `_all_parse_datetime` called `uniques.to_pylist()` on all distinct values (200k
  emails, about 10 ms of Python object creation) before testing the first one, which is what rejects ordinary text.
  The pattern-detection row sample (`RandomState(42).choice(n, 1000)`, a 4 ms permutation of 200k positions) was drawn
  on the critical path of the first text column, 15 ms in.
- Not a cause (measured, no change): rayon pool size (`RAYON_NUM_THREADS` 1, 2, 4), OpenBLAS threads, Python's GIL
  switch interval (5 ms to 0.05 ms), fewer column workers (2 workers: pool 0.125 s), Arrow's memory pool
  (`ARROW_DEFAULT_MEMORY_POOL` system, mimalloc: medians equal, sys-time spread smaller with `system` but no faster),
  glibc `MALLOC_*` tuning (faults 15k to 10-12k, wall unchanged; not adopted, it would be a process-wide allocator
  setting from a library). P1-17 had already removed the other small-input costs (`dataset_to_dict` 0.4 ms).

## What was changed (Python only; Rust and kernel twins untouched; output unchanged)
- `readers.py`: `_block_size` sets Arrow's CSV block size to about size / (2 x threads) between 1 MiB and 16 MiB when
  reading with threads, so a small file is parsed and converted by several threads and no single large buffer is
  allocated cold. Files of 128 MiB and more, and single-threaded reads, keep the 16 MiB blocks (d2.csv 204 MB, d3.csv
  471 MB and d4.csv 136 MB are read exactly as before; d1.csv 7.7 MB and the multi-table files, orders.csv 8.7 MB, customer.csv
  1 MB, now use 1 MiB blocks).
  Arrow types a column from all blocks (a later block that does not fit widens the whole column), so the schema is
  independent of block size; `_refine_integers` re-reads with the same options.
- `table.py` (`_profile_cols`, thread path only): columns start in order of `_col_work` (rows x kind weight: float,
  text, timestamp, others) instead of `_col_cost`, so `email` starts in the first wave; the process-pool order and the
  serial order are unchanged. The pattern sample is drawn on a side thread at pool start. The correlation's column-fill
  thread pool is used from 1,000,000 rows (was 100,000): at 200k rows a copy is under a millisecond and the extra
  threads compete with the column workers. All of this is order of work only; results are stored by column index.
- `column.py`: `_all_parse_datetime` converts the distinct values 256 at a time and stops at the first that does not
  parse (same result: it returned `all(...)` over the values in order, which also stopped at the first `None`).
- `tests/profile/test_small_input_fixed_cost.py` (new, 10 tests): block size rule; a multi-block CSV with columns that
  change type in a late block reads identically (schema, table, `_csv_cols` kinds) to the 16 MiB single-block read, and
  its profile equals the single-threaded profile; `_all_parse_datetime` stops at the first failure and checks every
  value across slice boundaries; the thread pool starts float and text columns first and the serial order is unchanged.

## What this does and does not show
- Measured here, on a 2.10 GHz Xeon with 4 vCPUs, d1.csv Shape is 0.09 s median (harness) and 0.090 s (A/B, 15 runs),
  against 0.110 s for the code before; the worst run in 15 is 0.119 s. The target was <= 0.13 s with >= 12x: met here
  (15.4x on this VM's baseline; the lead's baseline of 1.70 s would give 18.9x at 0.09 s).
- I could not reproduce the lead's 0.18 s for the code before the change on this VM (here 0.10 to 0.14 s), although the
  single-thread speed is the same. The lead's multi-thread run equals its single-thread run (0.18 against 0.17), which
  looks like less parallelism or more page-fault cost on that VM than on this one. The affinity rows above are the
  closest stand-in: with 2 CPUs the change is 0.107 s and with 1 CPU 0.171 s. **If the lead's VM effectively behaves like
  one CPU, this change does not reach 0.13 s there (about 0.17 s, a gain of only about 0.01 s over the baseline); on 2 or
  more effective CPUs it does.** What remains at that level is CPU work that is not in Python: the pyarrow CSV parse
  (about 0.04 s), `count_numeric` 4 x 8 ms, `value_counts_str` 2 x 11 ms, `fit_distribution` 4 x 6 ms, and about 15,000
  page faults. Cutting those further means changes in `rust/shape-kernel` (a cheaper first-seen counter and fewer
  temporary vectors in `count_numeric`) which I did not do without a measured need and a second equivalence round.
- Not tried: setting glibc/Arrow allocator parameters from the library (rejected above as too intrusive for a library);
  reading the CSV in a streaming way to overlap parsing with profiling (Arrow's streaming reader types columns from the
  first block only, which would change results).
