## Question for the lead

Wanted 6 requires `Connection.fetch_df_batches` on python-oracledb 3.0 and later,
with a documented catalog-to-Arrow map; Wanted 4 writes RAW/BLOB, CLOB and
INTERVAL DAY TO SECOND. Wanted 7 prescribes `[oracle] = oracledb>=3.0`.
How should Oracle sources read those types when that required API does not
support them on the prescribed minimum driver?

Evidence inspected in this session: the published python-oracledb **3.0.0**
source distribution, `src/oracledb/connection.py`, defines
`fetch_df_batches(self, statement, parameters=None, size=None)` with no
`fetch_decimals` keyword. `src/oracledb/impl/base/metadata.pyx`,
`OracleMetadata._set_arrow_type`, accepts NUMBER, CHAR/VARCHAR,
BINARY_FLOAT/DOUBLE, BOOLEAN and DATE/TIMESTAMP types. Its final `else` raises
`ERR_ARROW_UNSUPPORTED_DATA_TYPE`. RAW, BLOB, CLOB and INTERVAL DAY TO SECOND
are absent. The installed 26.0.1 driver adds a per-call `fetch_decimals` option
and documents LOB support, so a fake alone would conceal this incompatibility.

Options:

1. Permit a bounded DB-API cursor fallback for types the driver's Arrow API cannot
   read. Keep the prescribed extra and use `fetch_df_batches` for supported
   types, while converting unsupported columns to Arrow batches explicitly.
2. Approve a higher minimum driver that supports the complete required type map,
   after verifying its binary, LOB, interval and decimal behavior.
3. Restrict the source type map and reject these generated Oracle types. This
   loses the promised write/read coverage and is not recommended.

Recommendation: option 1. It preserves the specified dependency minimum and
complete value fidelity, with a documented, tested bounded fallback. A change
from the required source API needs the lead's decision; implementation is
paused rather than weakening an acceptance test.
