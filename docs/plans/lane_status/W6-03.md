## Decisions and deviations for the lead

1. **Two families of gates.** The catalog's `gate:NAME` accepts both the validation gates of a
   scenario run (`null_check`, `uniqueness`, `row_count`, `referential_integrity`,
   `schema_conformance`, which the W5-05 answer keys use) and the gates of `shape verify`
   (`null_constraint`, `unique_constraint`, ...). A scenario gate counts as detected when
   `shape verify` reports its own name for it (`shape.scenario.results.GATE_ALIASES`:
   `null_check` is `null_constraint`, `uniqueness` is `unique_constraint`). The catalog uses the
   scenario names because the suite checks them against the scenario run.
2. **One catalog entry has no detection.** `out-of-order-events`: every value is still present and
   in range, so no check that looks at a column's statistics can see a change of order (a test
   asserts that nothing fires). Its `detected_by` is empty and it carries a required `gap` text that
   says why; `shape canary make` refuses it (exit 2) with that text. This is the one place the
   catalog says what Shape does not detect today (the issue says the catalog describes what Shape
   detects today). A `gap` key is part of the `shape-failure-catalog` format; it is allowed only on
   an entry with an empty `detected_by`.
3. **Canaries and game days are for failures planted in one batch.** A canary of, or a game-day
   injection of, a drift scenario (a column added, a category shift, ...) is refused with exit 2
   ("a change over time"). Detective packs are the same. The schema modes of the catalog are
   drift scenarios (W5-05's), so `canary make column-added` is refused; the detective pack
   `renovations` plants the four schema changes in one batch with the new `rename_column`,
   `drop_column`, `retype_column` and `add_column` defect kinds.
4. **Game-day injection retargeting.** A plan names the user's tables but a scenario names retail
   columns, so the injection plants each defect in the first column of the right kind of the n-th
   table the round lists (documented in `docs/GAMEDAY.md`; the report says which column was hit).
5. **Persisted formats are not in `shape.compat.KINDS`.** The seven formats of this package follow
   the check W5-05 introduced (`shape.scenario.library.formats.check_header`: an integer
   `version`, a newer version refused with an upgrade message, unknown keys refused) and each has
   a compatibility test. Adding them to `KINDS` pulls in `tests/state/test_kinds.py` (one real
   writer per kind), `tests/state/test_policy_doc.py` and the time-capsule corpus, so I left that
   to be done once for these seven and W5-05's four. `shape.library` is a new top-level package and
   is added to the import-linter list in `pyproject.toml` (a test requires it).
6. **A bug fix outside the list, in `src/shape/generation/engine.py`.** `shape generate --from
   PROFILE` printed "Wrote 1 csv files" and wrote none for a table whose correlated columns the
   copula fits (every dataset profile with numeric columns): the last `release()` of the streaming
   writer skipped tables in `copula`. A two-line fix and a regression test
   (`tests/generation/test_release_after_copula.py`, red before, green after). Needed for
   `shape generate --from dataset:NAME` to write anything.
7. **Integration fixes for the merged lanes** (separate commit, "reconcile the merged lanes' CLI
   registries"). W5-05's `suite run` and `seed` and W1-01's `migrate` were never in W1-14's
   registries, so five CLI test files failed on the merge: exit-code entries for `suite run`,
   `seed` and `migrate`; `suite run` in `machine.SPECS` (so it gets `--dry-run`) with a case in
   `tests/cli/test_dry_run.py`; `seed` in `NATIVE_DRY_RUN` and in the test's `STATE_WRITERS`;
   `exitcodes.apply_to` so `shape migrate --help` ends with its table; `docs/EXIT_CODES.md`
   regenerated. `ruff format` also reflowed one line in `tests/safecapture/test_readers.py`
   (W1-11's file, an E501). Drop or reconcile these when the lanes are merged in order.
8. **Stray folder.** A command of mine created an empty folder `/case1` at the root of the cloud
   container (an unset temporary directory variable). The sandbox refused to let me delete it. It
   is outside the repository and the working tree; nothing in the lane refers to it.
9. **Workflow change for the lead** (I cannot edit `.github/workflows/*`). "The `failure-modes`
   suite passes nightly": add to `.github/workflows/nightly.yml`, under `jobs:`, after `drift-sweep`:


## Deliverables

### 1. Failure mode catalog — done

- `src/shape/scenario/library/failure_modes.json` (`shape-failure-catalog`, version 1): 23 entries,
  all the required kinds (late-arriving records, out-of-order events, timezone and DST edges,
  encoding corruption, mid-series unit change, columns added/renamed/dropped/retyped, class-imbalance
  shift, concept drift, duplicate keys, truncated strings, null floods, referential orphans, volume
  spikes and empty loads, placeholder values) plus partial load, new category values, null-rate creep
  and numeric distribution shift. `detected_by` uses `drift:KIND`, `rule:RULE`, `gate:NAME`.
- Code: `shape/scenario/library/catalog.py` (format, validation, `verify_mode`, the document),
  `detect.py` (what fires: profile and diff both batches, check the defective batch against a
  contract learned from the clean one, run the gates), `defects.py` (twelve new defect kinds, built
  on the chaos temporal and volume mutators where they fit), 17 new scenarios with answer keys under
  `library/scenarios/`, `index.json` updated.
- `docs/FAILURE_MODES.md` is generated (`scripts/gen_failure_modes.py`, `--check` exits 1 when
  stale, in `make check`). `shape failure-modes list [--json]` / `show ID` (`cli/failure_modes.py`).
- Tests: `tests/scenario/test_failure_catalog.py` (format, every required kind, every check real,

  and boundary cases).
