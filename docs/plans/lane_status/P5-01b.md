Environment: Python 3.11.15, `~/.venvs/shape` (`.[dev]`, `.[advanced]`, `-e plugins/shape-domains`),

## What the pacer was already doing right

`EmitRunner` schedules by **absolute deadline** (`t0 + schedule.due_time(n)`), so sleep overshoot
never accumulates, and after a stall it sends the backlog back to back (unbounded catch-up, which
is what keeps a stalled second's count within tolerance when the stall ends inside the second).
A bounded queue of about one second of batches already prefetches ahead of the deadline, and the
generator is cheap (block 1 takes about 2 ms). None of that needed to change. What was wrong is
that the pacing thread could be stopped for tens of milliseconds by things that are not pacing.

With 20-event batches at 2,000 events/s a batch is 1% of a second, so the test's limits are
tight: any stall of the pacing thread of 50 ms or more is `max_lag >= 0.05`, and a stall that
straddles a second boundary moves `stall x rate` events from one second to the next (50 ms =
100 events = 5%).

## Root causes (in the runtime) and fixes

1. **Full garbage collection scanned the host's whole heap, holding the GIL.** A full collection
   costs time proportional to every tracked object in the process. Measured here: 130,000 objects
   (a bare process that imported pandas, scipy, sklearn, pyarrow, shape) 25 ms; 475,000 objects
   48 ms. The heap at the moment the emit tests run inside the full suite was 372,000 objects
   (logged), against 130,000 in an isolated run. That is the one difference between "10 of 10
   isolated runs pass" and "fails once in a while in the full suite": the isolated heap is under
   the 50 ms limit even when a full collection lands in the run, the suite heap is not, and a
   full collection fires whenever the survivors of the young generations pass a quarter of the
   long-lived total (the sink keeps every batch alive, so a realtime run produces survivors).
   **Fix:** a realtime run `gc.freeze()`s the objects that exist when it starts and
   `gc.unfreeze()`s at the end (reference-counted across overlapping runs, and a freeze the
   caller made is left alone), so a collection scans only what the run allocates.
2. **The checkpoint write (`fsync`) ran on the pacing thread.** Every `--checkpoint-seconds` the
   pacer paused for `flush` + the atomic JSON write. On a busy disk that is tens of milliseconds
   per checkpoint; it is also why `test_realtime_resume_starts_its_own_clock` showed `max_lag` of
   26 ms and 47 ms in two suite runs (checkpoint at 1 s) against 0.2 to 1 ms in the final runs.
   **Fix:** realtime runs write checkpoints on a writer thread (latest offset wins). The pacing
   thread still calls `sink.flush()` itself and only then hands over the offset it has delivered,
   so the writer never touches the sink and a checkpoint never passes an undelivered or unflushed
   event (at-least-once unchanged). A failed write is raised by the next submit or at close; the
   final checkpoint is still written synchronously before `run` returns. `--no-realtime` keeps its
   synchronous path (no thread, no freeze), so its throughput and the kill-9 behaviour are as
   before.

## Evidence

Regression tests (`tests/streaming/emit/test_runtime.py`), each run against the **pre-fix**
`runtime.py` and the fixed one:

| test | injected stall | before (pre-fix runtime) | after |
|---|---|---|---|
| `test_realtime_rate_holds_through_a_full_collection_of_a_large_heap` | `gc.collect()` on another thread at 0.93 s, heap grown until a full collection takes at least 0.2 s | first form of the test: `per_second` `[1880, 2120, 2000, 2000]` (second 0 short by 6%), `max_lag` 0.144 s; final form: `max_lag` 0.2115 s, fails | passes (6 of 6 runs) |
| `test_realtime_rate_holds_while_the_checkpoint_write_is_slow` | every checkpoint save sleeps 0.4 s (a very slow `fsync`) | `max_lag` 0.394 s, fails | passes (6 of 6 runs); also asserts the saved offsets only increase and the last is 8,000 with `complete` |

The two regression tests use allowances of half the injected stall (`max_lag`), 10% per second and
5% overall, not the criterion's own 5% / 0.05: they exist to prove that the injected stall no
longer reaches the pacing, and the host-level stalls below would otherwise make them flaky. The
acceptance test itself is untouched.

Natural failure: **not captured.** Without the fix, 4 complete full-suite runs here
(`SHAPE_KERNEL=rust`, 4,428 tests each) all passed, with a logging plugin (outside the repo)
recording every realtime run's `per_second` and `max_lag` (runs 1 to 3: the full-collection count
was the same before and after the emit tests; run 4: no collection above 5 ms in any emit test), so the lead's 1-in-4 failure was not reproduced as such. What was
reproduced is the mechanism (the injected full collection above, and measured collection cost vs
heap size). With the fix, 3 rust runs, 1 python-kernel run and the isolated loops passed (below).

## Residual: host-level stalls the runtime cannot remove

While looking for a natural failure I found that this VM stops **every thread of a process** for
20 to 80 ms now and then, independently of the runtime:

* A shape-free analogue (a thread waiting on absolute 10 ms deadlines plus a 1 ms ticker, no
  shape code, no allocation) over 120 s: ticker gaps of 36.2, 23.6 and 20.0 ms, worst pacer lag
  19.4 ms.
* During stalls of 50 to 80 ms inside real runs (9 stalls above 20 ms in 100 runs of 4 s, in
  bursts such as 57, 54, 25 ms and 56, 66, 27 ms) a stack dump of all Python threads showed every
  one idle in `Event.wait` or `Queue.put`: no Python code held the GIL, GC had not run (gc
  callbacks), and the checkpoint writer did not exist (no checkpoint).

A stall of the whole process delays every delivery by definition, and a stall that crosses a
second boundary moves events between seconds; no pacing algorithm (more catch-up, prefetch, a
lead) can hide that, because the test counts deliveries by wall clock. So `max_lag < 0.05` over a
6 s run has a floor failure rate on a host that stalls like this one. This is reported rather
than worked around; the test was not touched. If the lead's VM stalls more than this one (it
runs several builders at once), the remaining 1-in-N failures would be this, and the options are
the owner's (§0.4): run the realtime rate tests on a quiet runner, or restate the CI criterion in
terms the host cannot violate. Nothing here changes a gate.
