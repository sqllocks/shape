## Findings and open items for the lead

1. **hr medium fails T-21 for `shape` on int/INT-18** (email, phone vocab; phone distinct ratio).
   This belongs to the P6-01 domain lanes, not P8-02; until it and any other failing domain are
   fixed the nightly is red, which is the correct outcome. The other 12 non-retail domains were
   not run locally (time); the first CI night will list every failing workload.
2. **Apply the workflow diff together with this branch.** `run.py --full` now includes `shape`
   generation for every domain; the old single `benchmarks-full` job would exceed the 6-hour
   hosted-job limit.
3. **Publishing to the docs site.** The workflow builds `PERFORMANCE.md` from the night's merged
   results and uploads it (artifact `parity-suite`) with the history; it does not push to the
   repository (the workflow has `contents: read`). Committing the nightly results/page, or having
   the P8-03 docs build pull the latest artifact, is a lead decision. The committed
   `docs/PERFORMANCE.md` is generated from the committed `results.json`; a test fails if they
   drift, so whoever commits a new `results.json` must rerun `scripts/gen_performance_page.py`.
4. **Streak rules** (`nightly.py streak`): only scheduled full-suite runs count, one per UTC day,
   and a red night or a missing day ends the streak. The history is carried between nights in an
   Actions cache (`nightly-history-*`) and uploaded every night; it can also be checked from the
   run list with the GitHub tools.

  `domain_workloads` with the same assertions.

- Scheduled runs (`on: schedule`) fire from the repository default branch, `main`. The scheduled
  7-night streak therefore starts only once build/main-plan reaches `main` (owner action).
  Until then, runs dispatched on build/main-plan (`workflow_dispatch`) give early signal; they
  are not counted by `streak --need 7`, which counts scheduled nights only.
