# FIX-339: default Microsoft Entra token scope in shape-databases

Branch `fix/339`, started from `fix/DEMO-LIVE` at 1d4e031. Fixes sqllocks/shape#339.

Status: **done**.

## The bug

`plugins/shape-databases/src/shape_databases/_auth.py` set
`ENTRA_DB_SCOPE = "https://ossrh-postgresql.azure.com/.default"`. Microsoft Entra knows no such
resource, so `credential=DefaultAzureCredential()` (or any credential object or `scope -> token`
function) could not sign in to Azure Database for PostgreSQL or MySQL unless the caller also gave
`token_scope=`.

## Sources (Microsoft Learn, read 2026-10-05)

- Azure Database for PostgreSQL flexible server, "Connect with Managed Identity":
  https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/how-to-connect-with-managed-identity
  (canonical: https://learn.microsoft.com/en-us/azure/postgresql/security/security-connect-with-managed-identity).
  The IMDS request uses `resource=https://ossrdbms-aad.database.windows.net`; the C# sample asks
  `DefaultAzureCredential` for `"https://ossrdbms-aad.database.windows.net/.default"`.
- Azure Database for MySQL flexible server, "Set up Microsoft Entra Authentication":
  https://learn.microsoft.com/en-us/azure/mysql/flexible-server/how-to-azure-ad
  (canonical: https://learn.microsoft.com/en-us/azure/mysql/security/security-how-to-entra).
  Section "Use the recommended Microsoft Entra token audience" lists the scopes: public
  `https://ossrdbms-aad.database.windows.net/.default`, US Gov
  `https://ossrdbms-aad.database.usgovcloudapi.net/.default`, China
  `https://ossrdbms-aad.database.chinacloudapi.cn/.default`, and says tokens for other audiences
  stop working from January 2027.

## Which engines use the scope

`resolve_password(..., scope=ENTRA_DB_SCOPE)` is called by:

- `_base.SqlSink.resolve_auth`: **PostgreSQL** and **MySQL** (both use the same `ossrdbms-aad`
  scope per the sources above, so one constant serves both; no per-engine scope is needed).
- `snowflake.SnowflakeSink.resolve_auth` (when no `private_key` is given): a `credential` object
  would also be asked for this scope. Snowflake has no fixed Entra resource (External OAuth uses
  the customer's own app registration), so there is no correct default to give it; `token_scope`
  is the way to set one. Behaviour unchanged by this fix; noted for the lead.
- `databricks.DatabricksSink.resolve_auth`: passes only `{"password": token}`, so the
  `credential` path and the scope are never reached.
- `duckdb_sink.DuckDbSink`: does not use `_auth` at all (no password, no credential).

The `token_scope` override is unchanged (`options.get("token_scope") or scope`).
