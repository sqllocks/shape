### What changed (all values unchanged; tests in both kernels)

1. **Allocator, one place** (`src/shape/_process.py`, called by `shape/__init__`, so the command line and the Python API
   alike): `import shape` sets `ARROW_DEFAULT_MEMORY_POOL=system` when `pyarrow` is not imported yet (the command line always),
   so every Arrow user in the process, the Parquet encoder included, takes the system pool; when `pyarrow` was imported
   first (the harness's order, many API users) its C++ pool can no longer change, so transparent huge pages are switched off for
   the process (`prctl(PR_SET_THP_DISABLE)`, Linux), which removes the `MADV_HUGEPAGE` first-allocation stall. A value the
   environment already has is kept; `SHAPE_MEMORY_POOL=default` turns it off. Tests: `tests/generation/test_process_allocator.py`
   (7, fresh interpreters: both import orders, the command-line module, opt-out, explicit user choice, `prctl` takes effect,
   values equal with and without it). Docs: `docs/GENERATION_ENGINE.md`, `CHANGELOG.md`.
   *Behaviour note for the owner:* a library import now changes the Arrow pool / THP setting of the embedding process
   (documented, opt-out exists). Say if you want it limited to the command line and `Engine.generate`.
2. **Text pools built from the file bytes** (`providers._lines`): a cold `first_name`/`last_name`/`email` column spent 10 to 20
   ms building its pool with a Python loop (about 10,000 `str.encode`) on the critical path of level 1; the numpy
   construction gives the identical array in 0.05 to 0.4 ms. Tests (`tests/generation/test_provider_pools.py`, 19): every shipped
   pool and edge cases equal the plain definition. Generation-only wall of education fell from 0.100-0.109 s to 0.076-0.092 s.

   inside `Engine._generate`): numpy C 35%, libc/malloc/page-fault 23%, Python frames 16%, Arrow C++ 15%, Rust kernel 10%
   (`spy_classify_financial.txt`). By source line the largest is `kernel_ops.pool_take` at 8.0%, then distribution `draw` 6.5%,
   `rng.uniform` 5.1%, `alias_draw` 4.2% and then a flat tail of 1-3% entries (`spy_hot_lines_financial.txt`). The same
   table warm against in-run: an `enrollment` chunk costs 225 ns/row on one warm thread (65,536-row chunk) and 600-760 ns/row
   inside the run (32,768-row chunks of `timeline_education.txt`: 19.7-25 ms): fresh pages, cold caches and contention. The
   allocator work attacks that factor; it lowered CPU-s by 23-28% in the interleaved comparison (retail 2.157 -> 1.642,
   capital_markets 0.645 -> 0.494, education 0.350 -> 0.270, financial 1.822 -> 1.303).
3. **The Python share is about 16% of samples, not the larger part of the run**, so a native pandas-free core for "the Python
   overhead" removes at most that share; the cost is in the 40-odd small numpy/Arrow steps per column, each allocating its own
   temporaries (the 23% in libc and page faults). pandas is not imported at all on the generation path (`arrowkit`, P4-10).
   Moving those steps into fused native functions means re-implementing about fifteen strategies in Rust, each with a
   pure-Python twin (T-03) and the same values (T-16): a far larger change than this work package, so I did not start it.
4. **Option (c) in the form T-17 allows does not help.** The writer tail is real (education: generation ends at 0.084 s and the files are
   complete at 0.119 s, because `enrollment`'s 160,000 rows are one row group encoded at close; `timeline_education.txt`). Smaller row groups so the
   encoding overlaps generation were measured interleaved, 20 runs each, at least 4 or 8 groups per table
   (`old_vs_new/rowgroup_rule_*.txt`): education +0.8% / +4.2%, capital_markets +1.0% / +3.7%, financial -0.3% / +3.3%, retail
   +5.4% / +5.7% (slower), and files 1-4% larger. A fixed 128k or 64k group size in the first probe was within noise too. pyarrow's
   `ParquetWriter` has no threaded write for one file (`use_threads` exists for reading only) and row groups of one file cannot be
   encoded concurrently by it; concatenating separately encoded groups would need a footer writer. A real parallel encoder is a
   **native Parquet writer** (arrow-rs `parquet` crate), which replaces T-17's "pyarrow `ParquetWriter`" and adds a dependency
   to T-02's pinned set: an owner decision, so I did not build it. It would attack the 0.035 s tail of education and the serial encode
   (0.40-0.47 CPU-s of financial); I have not measured what it would give, and encoding is about a third of the CPU time (education 0.08 of 0.27 CPU-s, financial about 0.43 of 1.30), so about two thirds would remain.
5. Allocator tunables on top (`MALLOC_TOP_PAD_`, `MALLOC_ARENA_MAX`, `MALLOC_MMAP_THRESHOLD_`): 7% on education in 10 interleaved
   runs, noise level, not adopted (as P4-10 found for retail).
