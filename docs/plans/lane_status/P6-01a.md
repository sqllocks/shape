## What was built

  (`pyproject.toml`, additive), each with `data/<domain>/schema.json` (3nf) and `schema_star.json` and its
  `reference/*.arrow` (Arrow IPC, as retail). The schemas are the baseline's dumps in

  `shape_domains/_packaged.py` is the shared loader (`PackagedDomain`: schema per mode, datasets, borrowed datasets);
  retail's module is untouched.
- **`benchmarks/vs_spindle/domain_1to1/export_domains.py [--check] [--domain D]`** writes those files from the
  baseline's dumps and checkout and proves them equal (`--check` exits 0; `export_retail.py --check` still exits 0).
- **D-10 notices:** `THIRD_PARTY_NOTICES.md` carries the MIT notice for the carried-over reference data (same
  copyright holder). The word is allowed there only (`check_user_facing` skips that file).
- **Engine/strategies: no change was needed.** Everything the three schemas use already existed
  (`record_sample`/`record_field`, `self_referencing`, `correlated`, `derived`, `formula`, `pattern`,
  `reference_data`, temporal patterns). `trading_days` is not a pattern of either implementation: both treat it as
  uniform.
- **Two schema facts that differ from the "dump + `unit: ns`" rule of retail** (both in `export_domains.py`, both
  tested, both for lead confirmation):
  1. `unit: ns` now goes on every temporal column that is not `seasonal` (retail's rule was `pattern == "uniform"`;
     capital_markets' `daily_price.trade_date` has `pattern: trading_days`, which the baseline draws uniformly and
     writes as `timestamp[ns]`). `export_retail.py` got the same rule; its output is byte-identical (`--check` exits 0).

     `industries.industry_name` of `gics_sectors`, which its `reference_data` strategy does not resolve, so its
     fallback yields `""` for all 61 rows (confirmed on the baseline's output). Equivalence (clause (e) vocabulary)
     needs the same values; a real nested lookup would be a product improvement and a deliberate departure.
- **Harness (all in `benchmarks/vs_spindle/domain_1to1/`; for lead confirmation):**
  - `verify.py`: (i) FK checks and fan-out accept text keys (capital_markets keys six tables by ticker; the verifier

  - `generate.py` (shape runner): the native kernel is imported before the timer (`get_kernel()`): it is an import

  - `seed_study.py` (new): the clause-(h) seed study (Shape seeds 1042-1049 vs the baseline floor).

## Escalation 2 - GEN-IN at medium (5.2x-7.8x; gate 10x), after one profiling round (plan 6.5 round 1)

Profile (py-spy, cProfile, a stamped timeline, `getrusage`; scripts not committed):

1. The three medium workloads are small: Spindle needs 1.17 s (capital_markets), 0.82 s (education) and 3.1 s
   (financial), against retail medium's 9.2 s. 10x means 0.12 s, 0.08 s and 0.31 s for Shape, including loading
   the domain and writing every table. Retail's 13.5x came from a baseline that spends 4.7 us per row; these
   domains cost the baseline 1.8-3.4 us per row.
2. Shape is CPU-bound on 4 vCPUs, not latency-bound: financial medium uses 1.0 CPU-seconds for 0.43 s of wall
   (2.3 cores of 4; user 0.85, system 0.15), of which generation is about 0.45 s single-threaded and Parquet encoding of the generated tables about 0.45 s (measured separately, one thread per table), the rest allocation and page faults. A perfectly packed run is 0.25 s, i.e. 12x, so 10x needs
   essentially no loss anywhere. Generation is already native (Philox, alias sampling, gathers; the Python
   overhead of the profile is about 15%).
3. Fixed costs per fresh process, measured: about 12 ms for the native kernel's first import (moved before the timer
   in the harness, T-19), and a bimodal 11-13 ms system-time stall (about half of the processes) on the first
   Arrow allocation, from mimalloc's 1 GiB arena with `MADV_HUGEPAGE` on a THP-`madvise` KVM guest (strace: the
   one `madvise`; `prctl(PR_SET_THP_DISABLE)` removes it, 0.1 ms). It is the effect the P4-07 note describes
   ("page-fault cost is large and bimodal"). `ARROW_DEFAULT_MEMORY_POOL=system` in the process environment gave
   up to about 20% on education (median 0.103 s against 0.132 s in one set of 15 fresh runs, 0.113 against 0.132 in another) and up to about 10% on financial (within noise in one set), less than the missing 35-45%; glibc malloc tunables gave about 5%, and P4-10 already measured them as noise.
   I did **not** switch the allocator process-wide (P4-07 deviation 2 left that to the lead).
4. P4-10's work (no pandas import, writer thread starts early, streamed aggregates, row groups of 256k rows, one core
   left to the writers) is in the base of this lane and already applied here; the level barriers of the engine cost
   little in these schemas (the long pole of every level is its biggest table, which has to wait for its parents).

Options (the gate is unchanged): (a) owner decides the sub-second medium workloads are GEN-IN at large (financial
18.7x; education 8.9x and capital_markets 7.0x there) or lowers the bar for them; (b) set the Arrow system allocator
process-wide in the CLI and the API (up to about +20% on these; P4-07 measured about 0.1 s on retail medium) and add a native, pandas-free
generation core (P4-10's option (b)); (c) a stronger single-file Parquet path (row groups encoded in parallel) which
pyarrow does not offer and which would need a native writer. I stopped after one profiling/optimisation round
because every remaining option changes more than this work package's scope (engine-wide allocator policy, a native
Parquet writer) or the gate, and §0.4 says to escalate rather than improvise. Say which and I continue (round 2).
