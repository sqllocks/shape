## Plan text that this work package does not follow (D-13, owner revision of 2026-09-30)

P4-08's text says `shape learn --spindle-json` writes a `.spindle.json`. D-13 supersedes it: Shape reads
and writes only its own formats and nothing user-facing names the baseline. So there is **no
`--spindle-json` option and no `.spindle.json` output**. `shape learn` writes a Shape generation schema
only. The equality with the baseline's `learn` is checked in the internal harness
(`benchmarks/vs_spindle/learn_1to1/`), which converts Shape's schema to the baseline's layout with P4-01a's
importer (`schema_import.py`). The LEARN-CLI row of §3.4 names `shape learn <file> --spindle-json`; the
timed command here is `shape learn <file> -o <out>`. `scripts/check_user_facing.py` is clean.

## What was built

- **`shape learn PATH [-o SCHEMA.json] [--format csv|parquet|jsonl] [--domain NAME] [--json]`**
  (`src/shape/cli/learn.py`): profiles a file, or a directory (one table per file), and writes the
  generation schema; `shape.generation.learn.SchemaBuilder` is the port of the baseline's `SchemaBuilder`
  (strategy per column: key, foreign key, pattern, date, enum, numeric distribution, text; relationships;
  small/medium/large scale presets from the row counts; correlated pairs at |r| ≥ 0.5; a `_row_id` surrogate
  key when a table has none). The output validates (`shape validate`) and runs (`shape generate SCHEMA.json`).
- **`shape generate --from X.shape`** (replaces the `NotImplementedError`): `shape.generation.fit.fit_schema`
  starts from the learned schema and fits it for generation, then `Engine` generates at the profile's row
  counts (`--rows N` for a one-table profile; `--scale` presets `profile`/`small`/`medium`/`large`; `--seed`,
  `--format`, `-o`, `--dry-run`, `--json` as for a domain). `shape.generate(profile)` and
  `shape.generate(profile, n=...)` do the same.
  - **Marginals**: an enum column draws with the profile's exact weights (`weighted_enum`); numeric columns draw
    from the fitted family (normal, uniform, log-normal, exponential, P4-05's families) or, when the fit is poor,
    from the quantiles (`empirical`); integers and booleans keep their type (new generator key `output_type`);
    floats get the decimals read off the observed minimum and maximum (`scale`); keys are a sequence, a uuid or a
    draw from the parent's keys; patterns map to built-in providers (new native `ipv4`, `postcode`, `zip_plus4`).
  - **Real Gaussian copula with marginal transforms**: for every pair of numeric, non-key columns with |r| ≥ 0.05
    the copula correlation `rho` is *calibrated* (`calibrate_correlation`: bisection on a fixed set of normal
    draws, through the actual marginals the engine will produce) so that the generated **Pearson** correlation
    equals the profile's (a Gaussian copula's Pearson correlation is not its `rho` for skewed marginals: for a
    log-normal and a normal, `r = 0.484` needs `rho = 0.614`). `Engine`'s copula post-pass reorders each column's
    own values by the rank of its correlated normal, so marginals are untouched. New engine options (schema
    `generation.output`): `copula_nulls: "rank"` (a column with nulls is reordered among its non-null rows; the
    default still skips it) and `copula_threshold` (the fit writes 0).
  - **Missingness**: each column's null rate per row (the engine's own null mask). Which values are missing
    together is not modelled (flagged).
  - **Seasonality**: `temporal` with the profile's month, weekday and hour weights within the observed range.
    Two small strategy extensions: `profiles.hour_of_day` takes one weight per hour (`"0".."23"`; before, any
    such dict was silently uniform) and `granularity: "day"` gives midnights (date columns). P4-05's
    `profile/temporal.py` detection works on raw columns; a `.shape` profile stores only the month, weekday and
    hour histograms (from the profiler's T-22 fields), so holiday lifts, tail index and trends are not in the
    profile and the plan flags `holiday_effects` as not modelled for every timestamp column.
- **`shape plan X.shape [--status S] [--rows N]`**: for every field of every column that has a value, plus row
  count, primary key, FKs, every correlation pair and dataset-level items, `preserved` / `approximate` /
  `not_modelled` with a reason (`ReconstructionPlan`, JSON). It no longer rejects profiles.
  `shape.plan(profile)` and `plan_reconstruction` do the same; portable evidence documents (`shape capture`)
  are still read, now checked item by item (G6).
- **Bugs G5 and G6** (Appendix A), see below.
- **Harness** `benchmarks/vs_spindle/learn_1to1/`: `baseline_learn.py` (runs the baseline's profiler +
  `SchemaBuilder` in `$SPINDLE_PY`, dumps its schema + correlated pairs), `compare.py` (field by field after
  `schema_import.to_native`, narrow named allow-list), `verify.py` (live on D2 / MT / D1), `baseline.py` (writes
  and `--check`s the committed fixture `fixtures/learn/d2_20000.json`), `bench_cli.py` (LEARN-CLI).
- Docs: `docs/GENERATION_ENGINE.md` ("From data"), `docs/GENERATION_STRATEGIES.md` (`output_type`,
  `granularity`, hour weights, providers), `CHANGELOG.md`.

## Acceptance, item by item

### 1. Profile → generate → profile within tolerance for the modelled fields — met

**Interpretation to confirm (lead).** T-22's tolerances (1e-9 on a mean, 1e-6 on a fitted parameter) compare two
*profilers* on the *same* data. A regenerated sample cannot match a source to 1e-9, so the test uses: **equality**
for structure (type, key flags, pattern, enum flag, which values an enum has, enum cardinality, min/max of an enum),
**five standard errors** for a statistic (null rate; enum weights; mean), **5 % of std** for std, a **sample-quantile
standard error** test for quantiles (density read from neighbouring quantiles, two samples, +3 % of std), **TVD ≤ 0.02**
for hour / weekday / month histograms, and **|Δr| < 0.02** for Pearson correlations. No tolerance of the plan was
changed; this is the reading of "within T-22 tolerances" for generated data and is documented in
`tests/generation/test_fit.py`.

`tests/generation/test_fit.py` is **tied to the plan**: it checks every field the plan calls `preserved` (strict) and
every `approximate` mean/std/quantiles (looser) on D2 (60,000 rows, CSV, 20 columns) — more than 150 claims measured —
so a field cannot be reported preserved without being measured. It already caught two over-claims while it was being
written (the uuid value list; the dtype of an all-midnight column), both fixed. Further cases: three correlated
columns with a log-normal marginal and 10 % nulls (|Δr| < 0.02 for all three pairs; x–y 0.484 → 0.490, x–w −0.309 →
−0.313), seasonal timestamps and dates, two tables with a key and FK (integrity 100 %), `--rows`.
Spot check at full size: D2 at 1,000,000 rows, profile → generate → profile, every column's dtype, null rate, mean, std,
pattern and family equal (script output in this session; only the unit-tested subset is committed).

### 2. `plan` flags every field that isn't modelled — met

`test_the_plan_covers_every_field_of_every_column` fails if any field of a column profile (that has a value) has no plan
item, or if the profiler adds a field that `COLUMN_FIELDS` does not know. `not_modelled` examples on D2: the values,
cardinality, length, uniqueness of e-mail, phone, ip and uuid columns; fit scores; which values are missing together;
dependencies other than the listed correlations; row order; holiday effects. `approximate` says how (e.g. a correlation
below 0.05 is "generated independently"; key-like names are never reordered by the copula, so a correlation with
`store_id` is `not_modelled`).

### 3. `shape learn` on D2 equals the baseline's `learn` except for listed, explained fields — met

`tests/generation/test_learn.py` compares Shape's schema for D2 (20,000 rows) with the baseline's, committed as a fixture
and re-checked against the live baseline (`baseline.py --check`: equal). Every column except two is equal in generator,
type and null rate; the two differences are named in the test **with the reason**:
`d2.wait_time` (`exponential`) and `d2.currency` (`enum_pattern`). On the full 1M-row D2
(`learn_1to1/verify.py d2 mt d1`, live baseline) one more column differs, `d2.order_value` (`truncated_enum`), and MT
has two (`orders.customer_id`, `orders.amount`, `truncated_enum`): 0 unexplained in all three datasets
(`evidence/P4-08/learn_verify_live.txt`). The four deliberate rules, in `shape.generation.learn.DIFFERENCES`:

| Rule | What differs | Why |
|---|---|---|
| `truncated_enum` | a numeric column with more distinct values than the profile lists (top 500) is generated from its distribution | the baseline draws only the 500 listed values, so the rest of the column's values never occur (`order_value`: 33,527 distinct values → 500) |
| `exponential` | an exponential fit is generated as an exponential (rate from the sample mean) | the baseline has no exponential generator and draws a normal with the same mean/std clipped to the range |
| `shifted_lognormal` | a log-normal fit with a location shift > 2 % of the column's level uses the quantiles | the baseline drops `loc`: a normal(50, 10) column fitted as a shifted log-normal came out as values near `exp(5.9)` clipped to the maximum (found by the copula test) |
| `enum_pattern` | a currency/language-code string column whose profile lists every value keeps those values | the baseline draws any code of a faker provider (vocabulary lost; needs the optional faker package). e-mail, phone, ssn, ip never become value lists (the schema would carry personal data) |

The comparison is not vacuous: `test_the_comparison_catches_a_real_difference`. Note for the lead: like the baseline, a
learned schema carries the *values and weights* of low-cardinality columns (names of categories) in the schema file.

### 5. Fixes G5 and G6 — each with regression tests that fail before the fix

`evidence/P4-08/g5_g6_before_fix.txt`: the 11 tests of `tests/regressions/test_g5_future.py` and `test_g6_plan.py`
**all fail** against the code of `lane/P4-10` (old `future.py`, `fidelity.py`, `api.py`), and all pass now.
- **G5** (`generation/future.py`): `missingness` returned the input unchanged (the mask was never applied) and
  `gaussian_copula` was a plain multivariate normal with no marginals (and clipping eigenvalues left variances ≠ 1).
  Now `missingness` returns an Arrow array with real nulls plus the mask, `gaussian_copula(corr, n, seed, marginals=)`
  maps `Phi(z)` through each marginal's quantile function and rescales the repaired matrix to a unit diagonal;
  `test_generating_from_a_profile_applies_both` is the product-path regression (nulls at the profile's rate, the
  correlation survives them). The module is now strict-typed and off the mypy ratchet.
- **G6** (`generation/fidelity.py::plan_reconstruction`): everything was `preserved` unchecked. Now a profile is planned
  from the schema that is actually fitted, and a portable evidence document is checked item by item (text with no top
  values → `not_modelled`; a correlation naming a missing column, a foreign key without `parent_count`, a conditional on
  a missing column → `unavailable`; numeric marginals → `approximate`, never `preserved`). Strict-typed, off the ratchet.
