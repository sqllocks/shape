Edits outside the new files, all small and additive: `cli/generation.py` (3 spots: the argument

Design decisions inside the work package (§0.3, none touches §2): the sink contract is Arrow
(`write_batch(table, RecordBatch)`, optional `finish_table`) so no data goes through numpy or pandas;
the Parquet sink writes `<dir>/<table>/part-NNNNNN.parquet` with the native Parquet sink of Shape (T-17)
and part *i* holds rows `i*chunk` to `(i+1)*chunk` whatever the batch sizes; `local_mp` is the engine's
threads (Shape's engine, scheduler and writer are reused, nothing ported twice); the process option
exists for the one case threads do not cover (part files encoded off the GIL, chunk-level resume), needs
the Parquet sink alone and a schema without a post-pass, and otherwise falls back to threads with a
warning; a table streams into a Fabric writer as it is generated (a bounded queue), not held until the end.

## Baseline defects found and fixed (owner's standing decision 2026-10-01: fix and record)

1. **`local_mp` writes the wrong number of rows.** `cmd_scale_generate` passes the *sum of all tables'
   rows* as the chunk budget, and `chunk_worker` scales each dynamic table by its share of the largest. Measured
   here (retail medium, baseline seed 43; `docs/plans/evidence/P6-13/baseline_local_mp_row_counts.txt`):
   `order` 786,160 and `order_line` 1,965,400, where `local_single` and the preset give 500,000 and
   1,250,000 (the other tables are static and equal). Foreign keys do hold (0 orphans,
   `baseline_fk_check.txt`). Shape: exact counts in every mode (asserted per mode in the tests and
   by the harness); the baseline's own output is the negative control that proves the harness catches it.
2. **Spark mode was not distributed and reported success unchecked** (from reading
   `notebooks/spindle_spark_worker.ipynb`; not run). It generated every dynamic table in the driver loop
   ("foreachPartition disabled"), wrote `{"rows_generated": total_rows, "status": "succeeded"}` whatever
   was written, installed a fixed older release of the package than the router's own, and built the
   OneLake token with the CLI credential only. Shape: executors make the large tables, the run fails
   unless every table has the spec's rows (`check_result`), the notebook installs the router's own
   version, and the storage token is an argument (or `azure-identity`).
3. **Jobs were lost with the process and held the token.** The job store was in memory (status and
   cancel returned `job_not_found` after any restart) and each record carried the bearer token. Shape:
   a durable private store, no credential in a record (settings are masked, and must be given again to
   resume), `resume` added.
4. **`StreamManager.stop` forgot a stream that had not stopped** (popped it before joining, so a stuck
   stream could never be stopped again) and the bridge's stream counted `chunk_size` rows per chunk
   rather than the rows written. Shape: a stream stays listed until it has stopped; `StreamState.record(rows)`
   counts rows written.
5. **Sinks held every table in memory until `close`** (lakehouse, warehouse, sql_database, kql) and
   `MultiStoreWriter` keyed results by class name (two writers of one class overwrote each other).
   Shape: a table streams into its writer (bounded queue); labels are unique.
6. A **bug of my own, found by a test and fixed:** a Fabric writer that fails after reading all its
   input left `WriterSink`'s drain waiting for a second end marker forever
   (`test_a_failing_load_names_the_sink…` hung before the fix).
