# `shape continue` and `shape time-travel` against the reference's incremental engines (P6-05)

```bash
source scripts/env.sh
"$SPINDLE_PY" benchmarks/vs_spindle/incremental_1to1/verify.py            # everything, about 70 s
"$SPINDLE_PY" benchmarks/vs_spindle/incremental_1to1/verify.py --only time-travel --scenario seasonal
```

Runs in the **reference venv** (it needs pandas and scipy and imports the reference's engines);
Shape runs as the product command (`$SHAPE_VENV/bin/shape`) in a subprocess. Exit 0 only when every
check passes. Writes `$BENCH_OUT_DIR/incremental_1to1/report.json`.

| file | purpose |
|---|---|
| `scenarios.py` | The scenarios and the fixed seeds (reference 42, its spread 43-46, Shape 1042: T-21, no option) |
| `baseline.py` | The reference's runs: `continue_from`, `TimeTravelEngine.generate`, and the same engine stepped one month at a time |
| `compare.py` | Exact checks, the T-21 column rule (the functions of `domain_1to1/verify.py`, loaded from that file), fan-out |
| `verify.py` | Orchestration, the allow-list with its witnesses, the negative controls, the report |

## Same starting state

Both tools start from one dataset: retail, `small`, generated by Shape with seed 1042 into
`$BENCH_OUT_DIR/incremental_1to1/start/` (Parquet, so types survive). `continue` reads that
directory in both tools. The reference's `time-travel` builds its own month 0, so its generator is
replaced, in the harness process only, by one that returns the shared dataset (the checkout is never
touched); Shape's month 0 for seed 1042 *is* that dataset (checked: `month0`).

## What is exact and what is statistical

**Exact** (deterministic, so no tolerance): table and column names, order and Arrow types; rows per
table and kind (INSERT, UPDATE, DELETE) equal the reference's, and the formula; new integer keys are
exactly `max+1 ... max+n`; DELETE rows equal the existing rows; UPDATE keys exist, are unique and keep
their foreign keys; inserted foreign keys have a parent; for time travel, snapshot dates, rows per
month and table (growth, churn and seasonality), new keys contiguous at the high-water mark, keys
unique, month 0 equal to the start, foreign keys intact in every snapshot.

**Statistical** (T-21 (b)-(e)): for every column of every kind of every table, Shape (seed 1042)
against the reference (seed 42):

* (b) null rate within `max(5 sigma, 1.5 x seed spread)`;
* (c) numeric and datetime KS within `max(critical value at alpha = 0.001, 1.5 x seed spread + 0.002)`;
* (d) categorical TVD within `max(3 x multinomial noise, 1.5 x seed spread + 0.002)`, vocabulary
  overlap at least 0.999 against the starting values.

Plus, because the output is a *change* and not a dataset:

* **row selection**: the positions in the starting table of the updated and of the deleted rows
  (uniform draws) are compared as a column;
* **how a value changed**: the fraction of cells that changed, the factor (new / old) of numbers and
  the shift in days of dates, per column of the UPDATE rows;
* **state transitions**: the observed next-state frequencies against the configured probabilities
  (TVD within 3 x multinomial noise), for both tools;
* **time travel, last snapshot**: every column against the reference's, and (T-21 (f)) the foreign-key
  fan-out (children per parent: coefficient of variation, share held by the top 1%, fraction without
  children).

### How the tolerances are derived

The *seed spread* is measured on the reference's own runs at seeds 42-46 and nothing else: the largest
distance (null rate, KS, TVD) between **any two** of its five runs. T-21 states the tolerance from
"Spindle's maximum seed-to-seed" distance; the domain verifier measures 42 against each of 43-46 (four
pairs). With five runs there are ten pairs, which is the same quantity with a better estimate of its
maximum. The seed set, the 1.5 multiplier, the 0.002 term, alpha and the 5 sigma / 3 x noise terms are
as in T-21. Nothing was adjusted after a run to make it pass.

Three derivations are this harness's own, stated before they are applied:

* **Effective sample size of inserts.** Inserted rows are clones of existing rows, so 2,000 inserts
  into a 50-row table carry 50 independent values. For INSERT rows the sampling-noise terms use
  `min(rows, rows in the table)` instead of `rows`; the seed-spread terms are unchanged.
* **Fan-out** has no critical value, so its tolerance is the larger of `1.5 x seed spread + 0.002`
  and 5 standard errors of the difference (a 200-resample bootstrap over the children), the
  sampling-noise term of the null-rate rule.
* **Time-travel columns are compared with the reference plus the documented repair** (below), run
  month by month, because the reference's snapshots contain foreign keys with no parent and their
  values cannot be compared with a snapshot that has none.

Columns of fewer than 30 rows on either side are reported, not asserted (`skipped_small` in the
report). `worst_ratio_to_tolerance` is the largest statistic / tolerance over all checked columns: a
value near 1 means a check is close to its limit.

## Allowed differences (the trust fixes)

Owner decision of 2026-10-01: a baseline behaviour that harms trust is fixed, with a narrow named
entry. Each entry needs a **witness**: a measurement in this run showing the reference exhibits the
defect and Shape does not. An entry with no witness fails the run (a stale allow-list).

| Entry | Reference behaviour | Shape | Witness in this run |
|---|---|---|---|
| `CONT-ZERO` | `update_fraction=0` or `delete_fraction=0` still updates and deletes one row per table | 0 changes | scenario `zero`: 9 + 9 rows vs 0 |
| `CONT-OVERLAP` | a row can be updated and deleted in the same delta | never | rows in both, 5 seeds |
| `CONT-DELETED-PARENT` | inserted children can reference a parent the same delta deletes | never | inserted rows pointing at deleted parents, 5 seeds |
| `CONT-CHAIN` | transitions are applied in sequence on the changed column, so a row can run through several states in one update | one step per row | `processing` rows: TVD 0.77 to the spec |
| `CONT-TRANSITIONS` | a transition naming an unknown column is ignored silently | error (exit 2) | the reference returns normally |
| `CONT-FK-COLUMN` | a foreign key draws from the parent's first integer `*_id` column | from the referenced column | not visible on retail (unit test) |
| `CONT-KEYS` | a non-integer primary key is cloned: duplicate keys | error | not visible on retail (unit test) |
| `TT-ZERO` | `growth_rate=0` still adds one row per table per month | none | scenario `zero_growth` |
| `TT-ORPHANS` | churn removes parents and leaves their children pointing at them: hundreds of thousands of orphans | children re-pointed at surviving parents in proportion to their children | orphans per snapshot, 5 seeds |
| `TT-ROUNDING` | an integer column changed by an update is truncated, so values fall (`product_category.level` gets a level 0 that never existed) | rounded | values below the starting minimum, 5 seeds |
| `TT-KEYS` | the key of a table is guessed, and a non-integer key is cloned | the declared key; error for a non-integer key | not visible on retail (unit test) |

For `TT-ROUNDING` the cross-tool KS of that one column is replaced by the property it protects:
Shape's values stay inside the starting values and its mean stays within 5 standard errors of the start's.
For `TT-ORPHANS` the reference's snapshots are repaired, independently of Shape's code, before the
columns are compared (see `compare.repair_orphans` and `baseline.run_time_travel_stepwise`).

Shape also differs from the reference in two places that are not defects and are not allow-listed
because the output is the same: booleans are left unchanged by an update in both, and the delta columns
are named `_shape_delta_type` and `_shape_delta_timestamp` (the harness maps them).

## Negative controls

The harness corrupts Shape's own output in 15 deliberate ways (a missing row, keys off by one, an
orphan, an altered delete row, a row updated twice, a changed foreign key, a row both updated and
deleted, a column 30% too high, a column with one value, a column with no values, a month that adds
nothing, an orphan in a snapshot, a repeated key, a final column 30% too high, and the unchanged column
as a control of the controls) and requires every one to be caught. The distribution controls run on the
`growth` scenario's 2,000 inserted rows: on the `default` scenario's 100 inserted rows a 30% shift is
inside T-21's own tolerance, which is a property of the rule, not of the harness.

## Known limits of the comparison

* One Shape seed against one reference seed (T-21). A tolerance fitted on five reference runs has a small
  false-failure rate: a diagnostic outside the harness (12 other Shape seeds from the same start, 12
  reference seeds) showed the two distributions of the borderline statistics overlapping.
* Month 0 of `time-travel` is generated by the reference with its own generator in the product command;
  the harness replaces it with the shared dataset, so the product command's month 0 is only checked
  against that dataset for Shape.
* The reference's command line has no `--seasonality`, `--update-fraction` or `--transitions` options; the
  harness calls its Python engine (the same one its command runs: checked equal at seed 43).
